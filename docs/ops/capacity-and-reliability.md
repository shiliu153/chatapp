# 容量与可靠性:一页讲清楚(2026-11-04)

> 用途:面试/简历/对外介绍时的**唯一数字来源**。每个数字都能点到证据文档,
> 标注了测量环境;不是「我做过压测」,是「我知道它在什么条件下是什么表现」。

## 1. 30 秒版本

> 一个 Flutter + Django + C++ 自建 IM 的交友应用,跑在 **2C2G 单机**上。
> 我把它压到过崩:极简读接口 **476 rps**(100 并发)、WebSocket **1000 连接 / 2000 条消息 0 失败**,
> 并逐个打崩组件测恢复:gunicorn <1s、imserver 3.2s、MySQL 2.6s。
> 压测里发现的真问题都修了:冷启动建会话死锁(819/1000 失败 → 0)、
> 广场列表 10 万条时 3.3 秒(→77ms)、配对通知突发把 imserver 延迟拖到 228ms(→24ms)。
> 还做了一次**归因式容量实验**:同机裸 WSGI 能跑 2626 rps、Django 只有 478 ——
> 读天花板是「Django 每请求 2.7ms + 2 核 GIL」,不是内存/容器(停掉观测栈只 +3.6%)。
> 另外补了 Prometheus + Grafana 观测和 10 条告警(规则与看板已就绪并校验,待上线),
> 设计目标是把故障发现从「人肉 curl」压到 **60 秒内**。

## 3. 三个能讲的故事

### 3.1 冷启动并发建会话死锁:819/1000 失败

**现象**:500 对全新配对同时发第一条消息,819 条失败,错误码 50001,日志刷 `deadlock retry exhausted`。

**根因**:`lock_pair` 先对「不存在的行」做 `SELECT ... FOR UPDATE`,RR 隔离级别下加的是**间隙锁**;
几百个事务抢同一段唯一键间隙,再各自 INSERT,互相死锁(1213)。重试 3 次、退避 2/4/6ms 扛不住。

**修复**:把 `INSERT ... ON DUPLICATE KEY UPDATE id=LAST_INSERT_ID(id)` 提到事务最前面(此时还没持任何间隙锁),
拿到 id 后按主键 `FOR UPDATE` 读 `last_seq`;重试提到 8 次并加线程本地抖动。

**验证**:先写回归用例,旧实现跑出 24–29/320 失败,新实现 0;再跑 500 冷会话端到端 500/500 ack。

### 3.2 广场列表 3.3 秒:聚合跑在 LIMIT 之前

**现象**:造 10 万条动态后,广场首屏 3354ms,而且 offset 0 和 50000 一样慢。

**根因**:注解里有 `COUNT(DISTINCT)`,MySQL 必须先把**全表**分组完才能 LIMIT。加了 `(created_at,id)` 索引也没用——
`exclude(author__profile__status=...)` 生成的 LEFT JOIN 让优化器放弃了索引,EXPLAIN 仍是 `Table scan + filesort`。

**修复**:两段式分页(先取当页 10 个 id,再只对它们聚合)+ 复合索引 + 把 LEFT JOIN 换成 `NOT IN` 子查询。

**结果**:3354ms → 77ms。剩余 77ms 里 `COUNT(*)` 占 45ms、深翻页 OFFSET 跳读占 106ms,
下一步是 count 缓存或 keyset 分页(要改三端契约,单独立项)。

### 3.3 配对通知突发:不是稳定性问题,是延迟问题

**现象**:500 对同时匹配 → 1000 条灰条瞬间入队。实测 500 条不限速:p50 **227.9ms**、p99 271ms、**0 失败**。

**根因**:20 个并发把 imserver 的 8 条 DB 连接池占满,请求在池上排队;所有人(包括正在聊天的用户)一起变慢。

**修复**:Celery 队列分级(`critical`/`default`/`notify`/`bulk`,**critical 不限速**——封禁不能被通知堵住);
`notify` 任务限速 50/s;队列深度进 `/metrics` 并配积压告警。

**结果**:p50 24.1ms(9 倍),p99 178.6ms;代价是总耗时 5.8s→11s。通知晚 5 秒无所谓,聊天 ack 被拖慢不行。

## 4. 简历口径(可直接用)

- 2C2G 单机支撑 **600 rps / 1000 条 WS 长连接**,定位并修复冷启动建会话死锁(失败率 82% → 0)。
- 主导可观测性建设(Prometheus + Grafana + 10 条告警),设计目标把故障发现压到 **60 秒内**;
  全栈崩溃恢复从 111s 收敛到 30s 的路径是「MySQL 看门狗 + 启动重试」,脚本已就绪待上线。
- 广场列表在 10 万条数据下 **3354ms → 77ms**:两段式分页 + 复合索引 + 消除 LEFT JOIN 对索引的抑制。
- 配对通知突发 p50 **228ms → 24ms**:Celery 队列分级 + 消费限速,保护 IM 写路径。

> 写简历时**不要**写「日活 X 万」——目前是封闭测试,真实用户个位数。
> 写「合成数据 10 万量级下 p99」比编 DAU 可信,而且经得起追问。

## 5. 追问预案

**Q:为什么不上 K8s / 微服务?**
A:2C2G 单机,拆开只会增加网络跳数和运维面;当前瓶颈是 MySQL 写与慢查询,不是部署形态。
K8s 解决的是「多机器编排」,这里连第二台机器都没有。

**Q:为什么不做分库分表?**
A:10 万用户量级,单表 10 万行。先把索引、分页、聚合形态修对(已经做了 43 倍提升),
比提前分片收益大得多;分片会让事务、唯一约束、跨表查询全部复杂化。

**Q:缓存一致性怎么保证?**
A:不用延迟双删,用**版本号**:键里带用户版本 + 全局版本,写路径只 `INCR`,旧键立即不可达。
避免了「删了又被并发读回填脏数据」的窗口。三防(空值哨兵/单飞锁/TTL 抖动)和 fail-open 都有测试。

**Q:限速是全局的吗?**
A:不是,Celery `rate_limit` 是每 worker 进程一份令牌桶,两个 notify worker 就是 2× 配置值。
要全局精确限速得把令牌桶放 Redis——当前规模不值得,这个取舍写在文档里。

**Q:这些数字能复现吗?**
A:能。`perf/run.py` 一条命令跑场景,输出带机器规格的 JSON;`perf/report.py` 对基线,
RPS −20% / p99 +20% 直接判回归。造数用 `seed_scale_users`,清理用 `--clean`。

**Q:怎么知道线上现在没坏?**
A:设计上 `/metrics` 暴露 RED + IM 连接/发送/死锁重试/池等待 + 队列积压;10 条告警推企业微信;
runbook 写清了「哪条告警 → 看哪块板 → 做什么」。**2026-11-03 已上线**:5 个容器(prometheus/grafana/
alertmanager/alert-relay/node-exporter)在跑,3 个 target(api/im/node)全 `up`。
仍未做的:探针 30s 粒度、告警接群机器人(现在只落日志)——这两条如实写在 `observability.md`。

- **读基线已重跑(2026-11-04)**:`perf/baseline.json` 的读点已换成 11-04 的量
  (`/app/config` @100 并发 = **476 rps**,三次 446–496)。11-01 的 608 是观测栈上线前量的,
  那 22% 的差**不是容器内存**(停观测栈只 +3.6%),而是 2 核上常驻进程更多、分走了 CPU;
  读的天花板本身是 Django 每请求 2.7ms + 2 核 GIL(同机裸 WSGI 能跑 2626 rps)。
- **写路径天花板低**:2C2G 上 `POST /discovery/swipe` 饱和 **~40 rps**(加并发只涨延迟),

  这两处都比「极简读 476 rps」更接近真实体感。11-03 那次 9.5s 的 p99 已归因为整机换页抖动。
- **候选池冷查询已优化一次(2026-11-04,D-3 选项 A)**:`CANDIDATE_CACHE_TTL` 30s → **300s**,
  60 秒同负载下缓存 miss **20 → 13**、miss 率 **3.33% → 1.67%**;试过的 `(status,shuffle_key,id)`

- **`app.log` 轮转已补(2026-11-04)**:此前 `/www/wwwlogs/chatapp/app.log` 不在 logrotate 里,
  每请求一行 JSON、持续高压约 1.4MB/5 分钟;现由 `deploy/ops/chatapp-logrotate.conf` 每天转、留 14 份、
  超 200MB 提前转,用 `copytruncate` 因为 gunicorn/celery 一直开着文件(见 `runbook.md` §7)。
- **观测栈已上线(2026-11-03)**:5 个容器(prometheus/grafana/alertmanager/alert-relay/node-exporter,
