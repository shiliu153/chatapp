# 双机负载均衡 vs 只升配:决策记录(2026-11-04)

> 对应 backlog **D-3**。输入:[双机负载均衡设计 v2](../superpowers/specs/2026-10-28-dual-server-load-balancing-design.md)
> (只有设计、无实施计划)+ [D-2 容量归因](read-baseline-2026-11-04.md)(2026-11-04 实测)。
> **本文只做决策,不含实施计划;拍板后才写 plan。**

## 0. 结论(推荐)

**不做双机;也先不升配。保持 2C2G,把「4C8G 升配」写成触发式预案(§5 的触发条件一出现就做,当天可完成)。**

理由三条,都能点到数字:

1. **项目定位是「个人项目、不对外发行」**(backlog §4.2)。双机解决的是「不挂站」,
   而当前真实负载远低于容量上限 —— 读 476 rps、写 40 rps、持续 30 分钟稳态 166 rps、
   WS 1000 连接 0 失败。为个位数用户买第二台机器,买到的是自己用不到的东西。
2. **跨云双活物理上不成立**(设计 v2 §2):Django 每请求串行打库,跨公网 RTT 会乘到每个请求上;
   媒体、IM 会话表也跨不过去。所以「两台一起做负载均衡」只有「同云同地域」一种形态,
   与「AWS 那台」无关。
3. **容量瓶颈是核数不是机器数**(D-2 §3.3):同机裸 WSGI 能跑 2626 rps、Django 只有 478 ——
   天花板是「Django 每请求 2.7ms × 2 核 GIL」。**加同云第二台 ≈ +2×(和升配到 4 核一样),
   但要付 1–2 周改造 + 一套双活运维;升配是控制台点一下。** 顺序天然是「先升配,不够再双机」。

## 1. 三个候选,四个维度

| | **S0 现状(2C2G 单机)** | **S1 升配(4C8G)** | **S2 同云双机(2×2C2G)** |
|---|---|---|---|
| 月成本增量(估算) | 0 | **+¥100–200**(规格差价) | **+¥60–100**(第二台轻量) |
| 容量预期 | 读 476 rps / 写 40 rps / 稳态 166 rps | **~2–3×**(核数 2→4 → GIL 天花板翻倍;8GB 内存**消除 swap**,长跑吞吐回到短测水平) | ~2×(两台各 2 核);IM 双活另有跨节点投递开销 |
| 切换/实施时间 | — | **当天**:控制台升配 + 重启,**停机 5–15 分钟** | **1–2 周**:NFS 媒体、MySQL 从库、Redis 从、IM 双活代码、nginx upstream、两次演练 |
| 合规影响 | 无 | 无 | 无(同云同地域) |
| 回滚 | — | 降配 + 重启(同 5–15 分钟);数据不受影响 | DNS 指回 A + 摘 B(600s TTL,**最坏 10 分钟**);B 上的从库/副本要拆 |
| 拿到 HA 吗 | ❌ 单点 | ❌ 单点 | ✅ B 挂无感;A 挂 10–15 分钟接管 |
| 运维面 | 1 台 | 1 台 | 2 台 + 双活一致性(媒体/IM/定时任务只能在一台跑) |

**明确不选的 S3**:AWS 跑 Django 跨云连 A 的数据库 —— 每请求多几百毫秒,**容量反而下降**(设计 v2 §2.1)。
AWS 那台的正确用途只有三个:海外静态/图片边缘缓存、**异地加密备份**、外部可用性探针(设计 v2 §5)。
其中「异地加密备份」已有替代方案(树莓派每日拉走,零成本),优先级也降了。

## 2. 为什么「先升配」而不是「先双机」

| 问题 | 升配能解? | 双机能解? |
|---|---|---|
| 读接口慢(每请求 2.7ms CPU × 2 核) | ✅ 核数翻倍 | ✅ 但要付 1–2 周改造 |
| 30 分钟长跑掉到 166 rps(`pswpout` +882MB) | ✅ 8GB 内存直接消除换页 | ⚠️ 每台 2GB 一样会换页 |
| 1000 并发突发丢 0.16% 连接 | ⚠️ 只能缓解 | ⚠️ 同样只能缓解(要调 `somaxconn`) |
| 机器整机挂掉(不挂站) | ❌ | ✅ **只有它能解** |
| 运维复杂度 | 不变 | 明显上升 |

也就是说:**除了「不挂站」,升配全面优于双机**;而「不挂站」对个人项目不是需求(挂了就挂了,
备份能恢复:双库 + 媒体 + 配置,每天 03:20 自建 + 03:30 宝塔 + 04:10 树莓派异地,RPO 24h、RTO ≈10min)。

## 3. 成本口径(估算,下单前以控制台实价为准)

- 轻量应用服务器升配:阿里云轻量支持「升级套餐」,差价按月计;2C2G → 4C8G 的差价区间
  **估算 ¥100–200/月**(设计 v2 §7 的口径)。**具体价格要你在控制台确认**,我不编数。
- 同云第二台 2C2G 轻量:**估算 ¥60–100/月**,另需买内网互通(同地域 VPC 内网免费)。
- 隐性成本(双机):每周多一套巡检、双活一致性排障、发布要两台同步 —— 这些不花钱,花时间。

## 4. 合规

- S0/S1/S2 全部**数据不出境**,无新增合规义务。
- 若将来把 AWS 那台用于「异地备份」:备份含手机号/聊天/照片,**属于个人信息出境**;
  个人项目虽无上架审查压力,仍建议**只放加密包**(`age`/`gpg`),且不接「境外探针抓取用户数据」这类用法。
- 悉尼 region 的边缘缓存只对澳/东南亚用户有意义;国内用户全量走它会 +150ms(设计 v2 §9)。

## 5. 触发条件:什么时候必须做(先写清,免得到时候靠拍脑袋)

**做 S1(升配)**,当下面任意一条成立:

1. 发现页(`GET /discovery/candidates`)p50 持续 **> 1 秒**(今天 0.62s),且 §6 的两个零成本优化已做完;
2. 同时在线 **> 100 人**(按 166 rps 稳态 ÷ 每人 1–2 rps 估算,100 人已贴近上限);
3. 出现「30 分钟长跑掉吞吐」的真实体感(即真的有持续高压场景,而不是压测)。

**做 S2(同云双机)**,只有当:

4. 你明确要求「站点不能挂」(例如给家人朋友长期用、或将来真要对外);
5. 且 S1 做完仍不够(读 > 1000 rps 或写 > 80 rps 的持续负载)。

**永远不做**:跨云双活、DNS 轮询做负载均衡、K8s/服务网格(设计 v2 §10)。

## 6. 零成本的容量手段(已拍板:先做这两条,排在花钱之前)

D-2 顺带发现的两条,都在「不花钱」这一侧:

1. **`CANDIDATE_CACHE_TTL` 30s → 300s**:冷池查询 114.6ms(2 万资料全表扫),热池 0.95ms。
   写路径已经用**版本号失效**(划走/配对/拉黑立刻让旧键不可达),所以 TTL 只是兜底,拉长不影响正确性。
   收益在**数据库侧**:每个活跃用户「每 30 秒一次 115ms 全表扫」变成「每 5 分钟一次」,
   冷查询频率降 10 倍;端到端 p50 影响很小(冷查询本来就是低频),别期待它把读吞吐从 476 抬到 550。
2. **`app.log` 加 logrotate**:每请求一行 JSON,持续高压 1.4MB/5 分钟且此前**没有轮转**。
   这条防的是「磁盘写满」,不是提性能(顺带省掉一点写盘)。安装见 `docs/ops/runbook.md` §7。

**口径更正**:本记录初稿写「这两条做完 100 并发读可能从 476 涨到 550+」——**不成立**:
`/app/config` 既不查库也不走候选池缓存,这两条改的是 DB 压力与磁盘风险。
真要把读吞吐拉上去,只有 §1 的 S1(升配)或砍 Django 每请求开销。

验证方式:`/metrics` 的 `cache_misses_total{name="candidates"}` 差值(比端到端 p50 直接),
结果见 [read-baseline-2026-11-04.md](read-baseline-2026-11-04.md) §8。
