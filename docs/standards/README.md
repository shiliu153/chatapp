# 编码规范

本目录存放本项目的**代码规范**,是「怎么写代码」的单一事实来源。规范与门禁成对存在:
每一份分册都对应一个可执行检查,不靠自觉维持。

## 分册索引

| 分册 | 适用范围 | 检查入口 |
|---|---|---|
| [python.md](python.md) | `chatapp/` 下全部 Python 代码 | `python config/comment_coverage.py`(`--structure` 看 Args 提示)+ `CommentCoverageTests` |
| Dart 分册 | `app/lib/` | 待立项 |
| TypeScript / Vue 分册 | `web/src/` | 待立项 |

## 三条通用原则

以下原则对所有语言分册生效,分册只负责把它们翻译成该语言的具体写法。

**一、注释解释「为什么」,不解释「是什么」。**
`i += 1  # 自增` 这类注释是噪音,代码已经说清了。值得写下来的是代码**看不出来**的东西:
为什么用子查询而不是 JOIN、为什么这里的顺序不能反、为什么这个参数不是它看起来的那个含义。
判断标准很简单——**删掉这条注释,后人重新踩坑的概率会不会上升**。

**二、改写注释时信息只增不减。**
本项目大量注释承载着踩坑结论与跨栈约定(如「IM 账号 = `u{user_id}`」「`BROKER_URL` 不能带
`CELERY_` 前缀」)。清理语气、格式、装饰符号都可以,但**技术结论一条都不能丢**。
规范化的目标是让结论更易读,不是让文件更短。

**三、规范由门禁维持,不靠自觉。**
没有门禁的规范会在三轮迭代内退化成「历史遗留风格 + 新代码各写各的」。因此每份分册都必须
配一个检查入口,并挂进 `python manage.py test` / `npm run test:run` 等既有门禁通道,
让违反规范的改动**在 CI 上红**,而不是在 review 里靠人眼抓。
