# 账号与鉴权

登录流程:**发送验证码 → 校验验证码换令牌 → 后续请求带 `access`**(access 过期时用 `refresh` 换新的)。

令牌规则:access 有效期 30 分钟,refresh 有效期 30 天;每次刷新都会轮换两个令牌(旧 refresh 立即失效);**同一账号可同时在线 1 个 App + 1 个网页,同类端互顶**(见 1.2 的「多端在线」说明)。

**端类型怎么定**:登录(1.2)与刷新(1.3)时按请求头 `X-Client` 判定端类型 —— 填 `web` 即网页端,**缺省(含不带该头)一律 `app`**;之后一律按令牌里自带的 `ct` claim 鉴权,**不再看请求头**。这样即使某个 Web 请求漏带 `X-Client`,也不会被当成 App 把真 App 顶下线。

### 1.1 发送短信验证码

> `POST` `/api/v1/auth/sms/send` · 无需鉴权 · 限流 20 次/小时(按 IP)

**接口描述**

向指定手机号下发 6 位短信验证码,用于登录。验证码 **5 分钟**内有效;同一手机号 **60 秒**内只能发送一次;校验连续错误 5 次会锁定 15 分钟。

**封闭测试白名单**:只有受邀名单内的手机号能收发验证码,名单外的号码在本接口直接返回 `403` + `40301`(不落码、不发送、不占 60 秒重发间隔)。名单存在服务端数据库里(`accounts.PhoneAllowlist`),由运营在审核台 **`/ops/allowlist/`** 维护 —— **加号/停用立刻生效,不需要重启服务**。`.env` 的 `SMS_PHONE_WHITELIST` 只作为「兜底种子」(库里没有该号码时按它放行;库里显式停用的号码优先被拒)。**本项目不接入短信商,白名单是长期机制**(不是过渡方案):任何新号码要能登录,都必须先由运营加进名单。

测试环境验证码固定为 `123456`,不会真实发送短信(见 [conventions.md §测试环境专用行为](conventions.md#测试环境专用行为))。

**请求参数**(Body,`application/json`)

| 参数名称 | 必填 | 类型 | 描述 |
|----------|------|------|------|
| phone | 是 | String | 中国大陆手机号,11 位数字(格式 `^1[3-9]\d{9}$`),最长 20 字符 |

**响应参数**

| 参数名称 | 类型 | 描述 |
|----------|------|------|
| status | String | 固定为 `"ok"`,表示已受理(不代表已送达) |

**请求示例**

```bash
curl -X POST http://<域名>/api/v1/auth/sms/send \
  -H "Content-Type: application/json" \
  -d '{"phone": "13800000001"}'
```

**响应示例**

成功:

```json
{ "status": "ok" }
```

60 秒内重复发送(响应头带 `Retry-After: 60`):

```json
{
  "code": 42901,
  "message": "发送太频繁,请稍后再试 预计 60 秒后可用。",
  "request_id": "fa18f86214b442d0b1b1c2f5a95c45d9"
}
```

**错误码**

| 错误码 | HTTP | 描述 | 处理建议 |
|--------|------|------|----------|
| 400 | 400 | 手机号格式不正确 | 检查号码是否为 11 位大陆手机号 |
| 40301 | 403 | 当前为封闭测试,该手机号未在受邀名单内 | 不可重试;需由运营在 `/ops/allowlist/` 把号码加入名单(立刻生效) |
| 42901 | 429 | 发送太频繁(同一手机号 60 秒间隔) | 按响应头 `Retry-After`(秒)等待后重试 |
| 429 | 429 | 触发 IP 限流(20 次/小时) | 按 `Retry-After` 等待;测试环境可换网络或稍后再试 |
| 50301 | 503 | 短信服务暂时不可用 | 稍后重试(服务端已回滚本次发送占位,可立即重试) |

### 1.2 校验验证码并登录

> `POST` `/api/v1/auth/sms/verify` · 无需鉴权 · 限流 60 次/小时(按 IP)

**接口描述**

校验短信验证码,通过后签发令牌。**未注册过的手机号会自动创建账号**(响应 `is_new_user: true`)。校验成功后有 60 秒的幂等重放窗口:响应丢失时用同样的号码与验证码再请求一次,会返回同一批令牌而不报错。

**多端在线**:同一账号可同时在线 **1 个 App + 1 个网页**,两端互不影响。**同类端互顶** —— 第二台手机(或第二个网页会话)登录会使前一个同类端的令牌失效:旧设备的后续请求返回 `401` + `code: 40101`,应清空本地凭证回到登录页。端类型由请求头 `X-Client` 决定(填 `web` 为网页端,**缺省 `app`**),之后按令牌里的 `ct` claim 鉴权。需要一次性下线所有设备时调用 1.5「退出所有设备」。

**运营账号不走短信登录**:`is_staff` / `is_superuser` 账号调用本接口一律返回 `403`(固定验证码 + 可猜的管理员手机号会直接交出最高权限身份)。运营人员请用 `/ops/` 的账号口令 + TOTP 登录;封闭测试确需用运营账号登 App 时,服务端可设 `SMS_ALLOW_STAFF_LOGIN=1` 放开(生产必须保持 0)。

**Web 端令牌下发方式**:请求头带 `X-Client: web` 时,`refresh` 不再出现在响应体里,改为通过 `Set-Cookie` 下发(`HttpOnly`、`SameSite=Strict`、`Path=/api/v1/auth/`),页面脚本读不到它;此时响应只有 `access`。App 不带该头,行为保持不变。

**请求参数**(Body,`application/json`)

| 参数名称 | 必填 | 类型 | 描述 |
|----------|------|------|------|
| phone | 是 | String | 中国大陆手机号,11 位数字 |
| code | 是 | String | 6 位验证码(长度必须正好 6 位) |

**请求头**(可选)

| 参数名称 | 必填 | 类型 | 描述 |
|----------|------|------|------|
| X-Client | 否 | String | 客户端类型。填 `web` 表示浏览器客户端:refresh 走 HttpOnly Cookie、响应体不含 `refresh`,并且**只顶掉网页端**的旧会话。缺省(含不带该头)按 `app` 处理 |

**响应参数**

| 参数名称 | 类型 | 描述 |
|----------|------|------|
| access | String | 访问令牌(JWT),后续请求放在 `Authorization: Bearer <access>`,有效期 30 分钟 |
| refresh | String | 刷新令牌(JWT),用于 1.3 换新令牌,有效期 30 天。**`X-Client: web` 时不返回** |
| is_new_user | Boolean | 是否本次登录自动创建的新账号 |
| user_id | Integer | 账号 ID。注意:与 `GET /api/v1/users/me` 响应里的 `id`(资料主键)不是同一个值 |

**请求示例**

```bash
curl -X POST http://<域名>/api/v1/auth/sms/verify \
  -H "Content-Type: application/json" \
  -d '{"phone": "13800000001", "code": "123456"}'
```

**响应示例**

成功:

```json
{
  "access": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.…(JWT,略)",
  "refresh": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.…(JWT,略)",
  "is_new_user": false,
  "user_id": 21
}
```

验证码错误:

```json
{
  "code": 40002,
  "message": "验证码错误",
  "request_id": "d5303c4f1db0435dab78c089218a42ff"
}
```

**错误码**

| 错误码 | HTTP | 描述 | 处理建议 |
|--------|------|------|----------|
| 400 | 400 | 参数不合法(手机号格式、验证码不是 6 位) | 检查请求参数 |
| 40001 | 400 | 验证码已过期,请重新获取 | 重新调用 1.1 获取新验证码 |
| 40002 | 400 | 验证码错误 | 提示用户核对;连续错误 5 次将锁定 15 分钟 |
| 40301 | 403 | 当前为封闭测试,该手机号未在受邀名单内 | 不可重试;需由运营在 `/ops/allowlist/` 把号码加入名单(校验入口同样拦截,码已下发也登不上) |
| 403 | 403 | 运营账号请使用运营后台登录 | 该手机号是 staff/superuser,改从 `/ops/` 登录;不要用固定验证码登 App |
| 42902 | 429 | 错误次数过多,请稍后再试(锁定 15 分钟) | 按 `Retry-After`(900 秒)等待 |
| 429 | 429 | 触发 IP 限流(60 次/小时) | 按 `Retry-After` 等待 |

### 1.3 刷新访问令牌

> `POST` `/api/v1/auth/token/refresh` · 无需鉴权 · 无额外限流

**接口描述**

用 `refresh` 换取新的 `access` 与 `refresh`。**每次刷新都会轮换**:响应的 `refresh` 是新的,旧的立即进入黑名单,不能再用。

**令牌来源**:请求体里的 `refresh` 优先(App 用法);没有时读 `chatapp_rt` Cookie(Web 用法)。带 `X-Client: web` 或请求里带该 Cookie 时,响应只返回 `access`,新 refresh 通过 `Set-Cookie` 下发。

**轮换宽限(60 秒)**:多个浏览器标签页同时刷新时,后到的请求可能拿着刚被轮换掉的旧 `refresh`。这类请求在 60 秒宽限内会拿到同一对新令牌而不报错;超过 60 秒的重复使用视为令牌泄露重放,返回 401。

被**同类端**的其他设备顶号后,旧设备的 `refresh` 也一并失效,刷新时返回 `401` + `code: 40101`;另一端(App 或网页)的 `refresh` 不受影响。

**端类型跟随令牌**:刷新时按 refresh 自带的 `ct` claim 校验该端的会话版本,换发出的 access 与轮换后的 refresh 都带同一个 `ct` —— 因此 Web 刷新出来的令牌永远是网页端,不会把 App 顶掉。

**请求参数**(Body,`application/json`)

| 参数名称 | 必填 | 类型 | 描述 |
|----------|------|------|------|
| refresh | 否 | String | 刷新令牌。Web 可省略,改由 Cookie 携带 |

**请求头**(可选)

| 参数名称 | 必填 | 类型 | 描述 |
|----------|------|------|------|
| X-Client | 否 | String | 填 `web` 时按浏览器客户端处理:响应不含 `refresh`,改为下发 Cookie。该头只影响响应形态,**端类型以 refresh 里的 `ct` claim 为准** |

**响应参数**

| 参数名称 | 类型 | 描述 |
|----------|------|------|
| access | String | 新的访问令牌(有效期 30 分钟) |
| refresh | String | **新的**刷新令牌(有效期 30 天),请覆盖旧值保存。Web 客户端不返回该字段 |

**请求示例**

App(请求体带 refresh):

```bash
curl -X POST http://<域名>/api/v1/auth/token/refresh \
  -H "Content-Type: application/json" \
  -d '{"refresh": "<refresh>"}'
```

Web(依赖 Cookie,请求体为空):

```bash
curl -X POST http://<域名>/api/v1/auth/token/refresh \
  -H "X-Client: web" \
  -b "chatapp_rt=<refresh>"
```

**响应示例**

App 成功:

```json
{
  "access": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.…(JWT,略)",
  "refresh": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.…(JWT,略)"
}
```

Web 成功(响应体只有 access,新 refresh 在 `Set-Cookie` 里):

```json
{ "access": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.…(JWT,略)" }
```

refresh 无效(格式错误 / 已过期 / 超出宽限期的重复使用):

```json
{
  "code": 401,
  "message": "登录状态已失效,请重新登录",
  "request_id": "355cf27ba8144811b15f04afa474f1b4"
}
```

**错误码**

| 错误码 | HTTP | 描述 | 处理建议 |
|--------|------|------|----------|
| 401 | 401 | 刷新令牌无效或已过期 | 回到登录页,重新走 1.1 / 1.2 |
| 40101 | 401 | 账号已在其他设备登录,请重新登录 | 本机已被顶号,清空凭证回登录页 |
| 403 | 403 | 跨站请求被拒绝 | 请求头 `Origin` 与本站不同源;正常页面不会出现,出现即视为 CSRF 攻击 |

### 1.4 注销

> `POST` `/api/v1/auth/logout` · 无需鉴权 · 限流 60 次/小时(按客户端 IP)

**接口描述**

结束当前会话:把本次的 `refresh` 加入黑名单,并清除 `chatapp_rt` Cookie。**幂等**——令牌缺失、已过期或已被拉黑都返回 204,客户端只需清空本地状态。

App 没有服务端会话可清时可以不调本接口(直接丢弃本地令牌即可);Web 因为 refresh 在 HttpOnly Cookie 里,必须调本接口才能真正清除。

带 `Origin` 请求头时(浏览器)会校验同源,跨站调用返回 403;该接口按客户端 IP 限流,防止匿名请求把黑名单表刷大。

**请求参数**(Body,`application/json`,可选)

| 参数名称 | 必填 | 类型 | 描述 |
|----------|------|------|------|
| refresh | 否 | String | 要拉黑的刷新令牌;Web 可省略,从 Cookie 读取 |

**响应参数**

无响应体(204),`Set-Cookie` 会清除 `chatapp_rt`。

**请求示例**

```bash
curl -X POST http://<域名>/api/v1/auth/logout \
  -H "Content-Type: application/json" \
  -d '{"refresh": "<refresh>"}'
```

**响应示例**

```
HTTP/1.1 204 No Content
Set-Cookie: chatapp_rt=""; expires=Thu, 01 Jan 1970 00:00:00 GMT; Max-Age=0; Path=/api/v1/auth/; HttpOnly; SameSite=Strict
```

**错误码**

| 错误码 | HTTP | 描述 | 处理建议 |
|--------|------|------|----------|
| 403 | 403 | 跨站请求被拒绝 | 请求头 `Origin` 与本站不同源;正常页面不会出现 |
| 405 | 405 | 使用了 GET 等非 POST 方法 | 改用 POST |
| 429 | 429 | 触发 IP 限流(60 次/小时) | 按 `Retry-After` 等待 |

### 1.5 退出所有设备

> `POST` `/api/v1/auth/logout/all` · 需鉴权 · 限流 60 次/小时(按客户端 IP)

**接口描述**

一次性下线**该账号的所有端**:两端的会话版本各 +1,本机与另一台设备的 access / refresh 全部失效;同时在服务端把该账号所有端的在线 IM 会话踢下线(走异步任务,不在响应路径上直连 IM)。

**用在哪**:手机丢了、怀疑账号被他人登录时。只想退出当前设备用 1.4「注销」;想在同类端换机直接重新登录即可(同类端互顶)。

**鉴权**:需要带 `Authorization: Bearer <access>`。令牌本身也要先通过会话版本校验,即被顶下线的旧令牌调不动本接口(返回 `401` + `40101`)。

**请求参数**:无请求体。

**响应参数**:无响应体(204),`Set-Cookie` 会清除 `chatapp_rt`。

**请求示例**

```bash
curl -X POST http://<域名>/api/v1/auth/logout/all \
  -H "Authorization: Bearer <access>"
```

**响应示例**

```
HTTP/1.1 204 No Content
Set-Cookie: chatapp_rt=""; expires=Thu, 01 Jan 1970 00:00:00 GMT; Max-Age=0; Path=/api/v1/auth/; HttpOnly; SameSite=Strict
```

**错误码**

| 错误码 | HTTP | 描述 | 处理建议 |
|--------|------|------|----------|
| 401 | 401 | 未带 access 或 access 已过期 | 先刷新或重新登录,再调用本接口 |
| 40101 | 401 | 账号已在同类端的其他设备登录,请重新登录 | 本机已被顶号,清空凭证回登录页 |
| 429 | 429 | 触发 IP 限流(60 次/小时) | 按 `Retry-After` 等待 |

### 1.6 登录设备列表

> `GET` `/api/v1/devices` · 需鉴权 · 无额外限流

**接口描述**

列出当前账号**登录过的端**:一类端一行,最多两行(`app` + `web`)。数据库里没有该端的会话行就不返回 —— 从没在该端登录过,就不会凭空多出一行。

`current` 标记「本次请求所在的端」,由请求头 `X-Client` 判定(填 `web` 为网页端,**缺省或取值未知一律 `app`**),因此结果里有且只有一项是 `true`。该头只影响本接口的 `current` 判定,不影响鉴权(鉴权一律看令牌里的 `ct` claim,见 1.2)。

**为什么没有「在线」字段**:在线状态是**账号级**的(见 [users.md §2.9 批量查询在线状态](users.md#29-批量查询在线状态)),按端拆分需要改动客户端心跳链路,收益不成比例。这里只给每端的「最近活跃时间」,由用户自己判断哪台设备还在用。别把 `last_active_at` 当在线判据 —— 一端挂着却没打请求,照样可能在线。

**最近活跃时间怎么来**:`last_active_at` 在该端**登录签发令牌**或**刷新令牌成功**时更新。批次 M 上线前就存在的会话行没有这个值,显示 `null`;该端下一次登录或刷新后才有。

**请求头**(可选)

| 参数名称 | 必填 | 类型 | 描述 |
|----------|------|------|------|
| X-Client | 否 | String | 填 `web` 表示网页端,`current` 落在 web 那行;缺省(含不带该头)按 `app` 处理 |

**响应参数**

| 参数名称 | 类型 | 描述 |
|----------|------|------|
| results | Object[] | 设备(端)数组,按端类型排序(`app` 在前);只含登录过的端,最多两项 |
| results[].client_type | String | 端类型:`app` 或 `web` |
| results[].client_label | String | 端类型的展示名:`App` / `网页端` |
| results[].current | Boolean | 是否本次请求所在的端(由请求头 `X-Client` 判定,只有一项为 `true`) |
| results[].created_at | String | 该端**首次**登录的时间(ISO 8601) |
| results[].last_active_at | String / null | 该端最近一次登录或刷新令牌的时间(ISO 8601);批次 M 之前建的行、或该端从未刷新过为 `null` |

**请求示例**

```bash
curl http://<域名>/api/v1/devices \
  -H "Authorization: Bearer <access>" \
  -H "X-Client: web"
```

**响应示例**

```json
{
  "results": [
    {
      "client_type": "app",
      "client_label": "App",
      "current": false,
      "created_at": "2026-11-09T10:20:31+08:00",
      "last_active_at": "2026-11-09T10:55:02+08:00"
    },
    {
      "client_type": "web",
      "client_label": "网页端",
      "current": true,
      "created_at": "2026-11-09T11:38:44+08:00",
      "last_active_at": "2026-11-09T11:38:44+08:00"
    }
  ]
}
```

(该账号 App 与网页端都登录过;本次请求带 `X-Client: web`,所以 `current` 落在网页端。)

**错误码**

| 错误码 | HTTP | 描述 | 处理建议 |
|--------|------|------|----------|
| 401 | 401 | 未带 access 或 access 已过期 | 先刷新或重新登录,再调用本接口 |
| 40101 | 401 | 账号已在同类端的其他设备登录,请重新登录 | 本机已被顶号,清空凭证回登录页 |
| 403 | 403 | 账号被重封禁(`banned_heavy`) | 当前账号全域不可用,联系客服;轻封禁不受影响 |
| 405 | 405 | 使用了 POST 等非 GET 方法 | 改用 GET |

### 1.7 下线指定设备

> `DELETE` `/api/v1/devices/{client_type}` · 需鉴权 · 无额外限流

**接口描述**

把**某一端**下线:该端的会话版本 +1,这台设备的 `access` 与 `refresh` 立即失效(下一次请求返回 `401` + `code: 40101`,客户端应清空本地凭证回登录页);服务端同时经异步任务把该端在线的 IM 连接踢下线。**另一端不受影响** —— 点掉网页,手机上的 App 继续用。

**幂等**:该端本来就没有会话行(从没登录过)、或重复调用,都返回 204,与 1.4「注销」口径一致。

**踢当前端**:允许。语义等同「注销本端」,服务端不做特判 —— 调用方拿到 204 后自行回登录页,不要假设服务端会替你保留令牌。

**与 1.5 的区别**:1.5「退出所有设备」是两端都 +1 并踢掉全部 IM 连接(手机丢了用);本接口只动路径里指定的那一端。

**请求参数**

| 参数名称 | 必填 | 类型 | 描述 |
|----------|------|------|------|
| client_type | 是 | String | 路径参数。要下线的端:`app` 或 `web`;其他取值返回 `400` + `40001` |

**响应参数**:无响应体(204)。

**请求示例**

```bash
curl -X DELETE http://<域名>/api/v1/devices/web \
  -H "Authorization: Bearer <access>"
```

**响应示例**

```
HTTP/1.1 204 No Content
```

**错误码**

| 错误码 | HTTP | 描述 | 处理建议 |
|--------|------|------|----------|
| 40001 | 400 | 客户端类型不合法,只能是 app 或 web | 检查路径参数,只支持 `app` / `web`。该码在登录接口里表示「验证码已过期」,按调用接口解读 |
| 401 | 401 | 未带 access 或 access 已过期 | 先刷新或重新登录,再调用本接口(注意:要下线的端失效后,用它自己的令牌也调不动本接口) |
| 40101 | 401 | 账号已在同类端的其他设备登录,请重新登录 | 本机已被顶号,清空凭证回登录页 |
| 403 | 403 | 账号被重封禁(`banned_heavy`) | 当前账号全域不可用,联系客服;轻封禁不受影响 |
| 405 | 405 | 使用了 GET 等非 DELETE 方法 | 改用 DELETE |
