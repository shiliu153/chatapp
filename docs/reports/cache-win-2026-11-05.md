# 候选池缓存的真实收益:开/关对比实测(2026-11-05,E-7)

> 结论先放:**命中率 97.8% 成立;「DB QPS −60%」不成立**(语句数只省 12%),
> 缓存真正省掉的是候选池那条 **171ms** 的查询 —— 关掉缓存后同负载吞吐 **−63%**、p50 **×28**。
> 数字来源:[capacity-and-reliability.md](../ops/capacity-and-reliability.md) §2/§3.4 引用了这里。

## 1. 为什么要做

缓存(2026-10-21 上线,`config/cache_utils.py` + `discovery/services.py`)上线时写的验收是
「**命中率 ≥90%、DB QPS −60%**」,一致性测试 13 条也是绿的 —— 但**这两个数字一直是断言,
没有任何实测出处**(backlog E-7 就是挂在这条上)。而「DB QPS −60%」这个说法本身可疑:
候选池缓存省掉的是**一条** SQL(池子查询),不是六成的语句。

## 2. 先补两个测量前提(PR #70)

1. **`CANDIDATE_CACHE_TTL=0` 原本关不掉缓存** —— `cache_utils.ttl_with_jitter(0)` 会把 0
   兜成 `max(1, ...)` = 1 秒,于是「把 TTL 调成 0」实际是「TTL 变 1 秒」,同一用户 1 秒内的
   重复读仍然命中。现在 `candidate_pool_ids` 里 **`TTL <= 0` = 显式关缓存**(直接查库、不读也不写),
   顺带成为线上可用的缓存熔断开关。
2. **`GET /discovery/candidates` 是 60 次/小时/账号** 的限流读接口,而 `perf/run.py` 的读连接
   是闭循环,10 个账号几秒就把额度打光(压出来的是 429)。新增 `--read-interval`
   给读连接限速,才能把「同等报价负载」跑满 30 秒。

| 服务 | gunicorn `-w 2 --threads 4`,MySQL 8.0.45,Redis 同机 |

## 4. 原始数字

### 4.1 两轮负载(同参数,唯一变量是缓存开关)

| 指标 | 缓存开(`e7-A-on.json`) | 缓存关(`e7-B-off.json` / `-off2.json`) |
|---|---|---|
| 请求数 | 446 | 169 / 173 |
| 吞吐 | **14.6 rps** | **5.4 / 5.5 rps** |
| p50 | **41.6ms** | **1199 / 1164ms** |
| p90 | 95.1ms | 1579 / — |
| p99 | 1304ms | 2158 / 1870ms |
| 错误 | 0 | 0(全部 200,没有 429,说明限速生效) |
| 缓存命中/未命中 | **437 / 10 → 97.8%** | 无缓存读写 |

### 4.2 数据库侧

| 口径 | 缓存开 | 缓存关 |
|---|---|---|
| `Questions` 增量 / 时长 | 3269 / 30.9s → **105.8 qps** | 1477 / 31.5s → **46.9 qps** |
| 空闲基线(无压测 20s) | **2.8 qps** | 同 |
| 每请求语句(整机口径,减基线) | **7.1** | **8.0** |
| 每请求语句(`CaptureQueriesContext`,只算接口) | **4** | **5** |
| 池查询耗时(2 万资料,5 次中位) | 命中 ≈0ms | **171.3ms**(min 155.5 / max 210.9) |

> 关缓存时整机 DB QPS **更低**不是「省了 DB」,而是**吞吐塌了**:同样 10 个连接、同样 0.6 秒间隔,
> 服务端只做到 5.4 rps,其余时间在排队。按同一吞吐 14.6 rps 折算,关缓存约 14.6×8.0+2.8 ≈ **120 qps**
> (对比 105.8,即 **+13%**)—— 语句数差异就是这么小。
> 真正撑不住的是**时间**:14.6×171ms ≈ **2.5 秒 DB 忙等/秒**,2 核不可能。

## 5. 口径与坑

1. **别再把「DB QPS −60%」写在任何地方**。能站住的说法是:命中率 97.8%、关掉后吞吐 −63%、
   p50 ×28,以及「省掉的是那条 171ms 的池查询」。
2. **池查询今天的实测是 171ms,比 2026-11-04 那次 115ms 更慢** —— 同一台机器、同样的 2 万资料,
   差别来自 buffer pool 冷热与建表统计(刚 bulk_create 完)。**别把这两个数当同一个基线**,
   引用时都带上日期。
3. **关缓存要重启**:`CANDIDATE_CACHE_TTL` 是启动时读的 `.env`,改完必须重启 `chatapp-web`
   (约 3 秒 502)。这也是为什么它适合当「熔断开关」而不是「随时可调参数」。
4. **限速读数**:`--read-interval 0.6` 下关缓存轮只打出 169–173 个请求(而不是 446),
   因为每条请求 1.2 秒才返回 —— 这不是限速失效,而是**延迟吃掉了报价**。对比「吞吐」时才公平。
5. **两轮的 p99 都比 p50 高一个量级**:开缓存轮是 10 个账号各 1 次冷启动(171ms)+ 整机抖动;
   关缓存轮是排队尾部。要判回归用同机同日同参数的配对比较,别跨日期比。
