## §2 读前必建概念

### 1）ORM 模型 = 一张表 + 一层 Python 类

每个 `models.Model` 子类对应一张表，每个字段对应一列。字段声明里的第一个位置参数是**中文 verbose name**（运营后台、报错信息会用到）。

### 2）字段类型与常用参数（本项目出现的全部）

| 写法 | 含义 |
|---|---|
| `CharField(max_length=20, blank=True)` | 字符串；`blank=True` 表示**表单/序列化层允许为空** |
| `DateField(null=True, blank=True)` | 日期；`null=True` 表示**数据库允许 NULL**（两者不是一回事：`null` 管数据库，`blank` 管校验） |
| `OneToOneField("自己或别处", related_name="profile")` | 一对一（一个用户一份资料） |
| `ForeignKey(..., related_name="photos")` | 多对一（一个用户多张照片） |
| `ManyToManyField(Tag, related_name="profiles")` | 多对多（资料 ↔ 标签），Django 自动建中间表 |
| `PositiveSmallIntegerField(default=0)` | 非负小整数 |
| `ImageField(upload_to="photos/%Y/%m/")` | 图片字段；`upload_to` 决定磁盘落盘路径（按年月分目录） |
| `DateTimeField(auto_now_add=True)` | 创建时自动写入当前时间 |
| `choices=Gender.choices` | 限定取值（`TextChoices` 枚举） |
| `on_delete=models.CASCADE / SET_NULL` | 被引用对象删除时本行的行为：级联删除 / 置 NULL |

### 3）`related_name` 是反向查询的名字

`Profile.user` 定义后，从用户对象反向拿到资料要用 `user.profile`（因为写了 `related_name="profile"`）。**同一个模型被两个外键指向时必须给不同的 `related_name`**——`Photo` 里 `user` 与 `reviewed_by` 就属于这种情况（`users/models.py` 第 107、112–113 行）。

### 4）迁移（migrations）

- `makemigrations`：对比"模型代码"与"已有迁移文件"，生成新的迁移脚本（Python，记录建表/改列操作）
- `migrate`：把迁移脚本执行到数据库
- `makemigrations --check --dry-run`：**只检查两者是否一致**，不写文件。本项目当前实测输出 `No changes detected`——说明模型与迁移完全同步。**你改完模型一定要跑这条命令确认。**

### 5）`@property` 不是数据库字段

`Profile.age`（第 72–74 行）是**算出来的**，数据库里没有 age 列。凡是要用 age 过滤数据库，就必须换算成 `birthday` 的范围查询——这就是 `birthday_bounds` 存在的原因。

### 6）在线状态为什么要自建

`users/presence.py` 第 1–4 行的注释写得很直接：腾讯云 IM 的在线状态能力**需要付费套餐，而且没有"最后活跃时间"**。所以本项目用 Redis 存"最后一次认证请求的时间戳"，"在线"= 距现在 ≤120 秒（`45s 心跳 × 2 + 余量`，第 15 行注释）。

## §3 精读清单

### 1. `users/models.py` 第 6–26 行 —— 三个日期函数（**最容易被跳过的宝藏**）

| 行 | 在干什么 | 要抓的点 |
|---|---|---|
| 6–8 | `calculate_age(birthday, today=None)` | 用元组比较 `(today.month, today.day) < (birthday.month, birthday.day)` 判断"今年生日过没过"。**不能用"年差"**，否则生日当天会算错 |
| 11–16 | `shift_years(day, years)` | 把日期往前推 N 年；`try/except ValueError` 处理 **2 月 29 日**（平年没有这天）→ 退化成 2 月 28 日 |
| 19–26 | `birthday_bounds(age_min, age_max)` | 把"年龄区间"换算成"生日区间"：`age >= age_min ⇔ 生日不晚于今天减 age_min 年`；`age <= age_max ⇔ 生日晚于今天减 (age_max+1) 年`。**目的：让筛选能走数据库索引**，而不是取出所有人再在 Python 里算年龄 |

**实测证据（2026-10-09，`today=2026-10-09`）**：

| 调用 | 结果 | 说明 |
|---|---|---|
| `calculate_age(2000-10-09)` | `26` | 生日当天 |
| `calculate_age(2000-10-10)` | `25` | 差一天 |
| `calculate_age(2008-10-09)` | `18` | 正好 18（**边界值**） |
| `birthday_bounds(18, 30)` | `(2008-10-09, 1995-10-09)` | 上界是 age_min 那天，下界是 age_max+1 那天 |
| `shift_years(2000-02-29, 26)` | `1974-02-28` | 闰日退化 |

### 2. `users/models.py` 第 29–44 行 —— 三个枚举

- `Gender`：`male` / `female`
- `ProfileStatus`：**四态** `incomplete` / `complete` / `banned_light` / `banned_heavy`
- `PhotoStatus`：`pending` / `approved` / `rejected`

> 用 `TextChoices` 而不是整数：数据库里存的是可读字符串，排查问题时一眼就懂（代价是占空间，可忽略）。

| 64 | `tags = ManyToManyField(Tag, ...)`——一个人多个标签，一个标签多个人 |

### 4. `users/models.py` 第 72–103 行 —— Profile 的四个行为

| 行 | 在干什么 | 为什么重要 |
|---|---|---|

| 76–90 | `missing_fields()`：缺 `nickname`/`gender`/`birthday`/`city`/`bio`/**photos（至少一张已过审）** 就记一项 | 这六项就是全项目"资料完善"的口径（`CLAUDE.md` 末尾有同样描述） |

### 5. `users/models.py` 第 106–133 行 —— Photo 与 Preference

| 行 | 要抓的点 |
|---|---|
| 107 | `related_name="photos"` → `user.photos` |
| 108 | `upload_to="photos/%Y/%m/"` → 文件按 `media/photos/2026/10/xxx.jpg` 存 |

| 15 | `ONLINE_WINDOW_SECONDS = 120` | "在线"的判定窗口（客户端 45 秒心跳） |
| 16 | `PRESENCE_MAX_IDS = 100` | 单次批量查询上限（P07 的接口会用它） |

## §4 动手实验

### 实验 1 · 在 shell 里把三个日期函数玩一遍

```powershell
cd D:\pycharmproject\chat_app\chatapp
python manage.py shell
```
```python
from datetime import date
from users.models import calculate_age, birthday_bounds, shift_years
calculate_age(date(2000, 10, 9))      # 用"今天"算
calculate_age(date(2000, 10, 10))
birthday_bounds(18, 30)

```
预期与 §3 的实测表一致（注意 `calculate_age` 的默认 `today` 是"今天的本地日期"，所以 2026-10-09 之后跑，第 2 行可能变 26——**这正是它接受 `today` 参数的原因：可测试**）。

### 实验 2 · 确认模型与迁移同步

```powershell
python manage.py makemigrations --check --dry-run
python manage.py showmigrations users
```
预期：`No changes detected`（已实测）；第二个命令列出 `users` app 的全部迁移与是否已应用 `[X]`。

然后**做一次破坏性实验**：给 `Profile` 临时加一行 `foo = models.CharField(max_length=5, blank=True)`，再跑 `makemigrations users` → 会生成一个新迁移文件。**看完内容后删掉该文件并还原模型**：
```powershell
git status --short chatapp/users/          # 应显示无改动
```
> 这个实验的价值：你亲眼看到"改模型 → 生成迁移文件 → migrate 执行"。**注意本项目要求迁移文件入库**，所以实验产物必须清掉。

### 实验 3 · 观察在线状态的三态

```powershell
python manage.py runserver 127.0.0.1:8000     # 终端 A
# 终端 B：先登录拿 access（P05 实验 1 的 $login.access）
Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/users/me -Headers @{ Authorization = "Bearer $($login.access)" } | Out-Null
docker exec chatapp-redis redis-cli GET presence:1        # 一串 10 位时间戳
docker exec chatapp-redis redis-cli TTL presence:1        # ≤ 604800
# 查在线状态
Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/presence?user_ids=1" -Headers @{ Authorization = "Bearer $($login.access)" } | ConvertTo-Json -Depth 5
```
预期 `online: true` + `last_active_at` 是 `+08:00` 结尾的 ISO 串。

**让它变"离线"（不用等 120 秒）**：
```powershell
$old = [int][double]::Parse((Get-Date -UFormat %s)) - 300
docker exec chatapp-redis redis-cli SET presence:1 $old
# 再查一次 → online: false, last_active_at 仍有值（"离线但知道最后活跃时间"）
docker exec chatapp-redis redis-cli DEL presence:1
# 再查 → online: false, last_active_at: null（"未知"）
```
> **这三态（在线 / 离线但有记录 / 完全未知）就是客户端显示逻辑的全部输入**，值得写进笔记。

## §5 自查题

**Q1. 为什么 `calculate_age` 不能写成 `today.year - birthday.year`？**

**参考答案**：今年生日还没到的人会被算大一岁。正确做法是算年差后再判断"今年生日过没过"（第 8 行的元组比较）。实测：2026-10-09 时 `birthday=2000-10-10` 应为 25 而不是 26。

**Q2. `birthday_bounds` 为什么必须存在？直接用 `age` 过滤不行吗？**

**参考答案**：`age` 是 `@property`（第 72–74 行），数据库里没有这一列，无法写进 `WHERE`。若在 Python 里逐行算年龄再筛，会把全表拉进内存。`birthday_bounds` 把年龄区间翻译成 `birthday` 的范围条件，使筛选能走数据库索引（推导见第 22–23 行注释）。

**Q3. `refresh_status` 里为什么第一件事是判断封禁态并 `return`？**

**参考答案**：否则每次保存资料（例如用户改个昵称）都会把 `banned_light`/`banned_heavy` 重算成 `complete`/`incomplete`，等于自动解封。注释写明这是 M1b/M3 的兜底。

**Q4. `Photo` 里两个指向 User 的外键，为什么必须写不同 `related_name`？**

**参考答案**：反向访问名在同一模型上会冲突（`user.photos` 与 `user.photos_reviewed`）。Django 要求显式区分，否则 `makemigrations` 直接报错。

**Q5. 在线状态为什么不用腾讯云 IM 的在线能力？**

**参考答案**：`presence.py` 第 1–4 行注释给出两条理由：IM 的在线状态需要付费套餐；且它**没有"最后活跃时间"**，而产品需要展示"最后活跃于 N 分钟前"。自建方案只需 Redis 一个 key + 认证时写时间戳。

**Q6. `touch()` 里为什么要包 try/except 并且只 `warning`？**

**参考答案**：在线状态是"点缀信息"，Redis 抖动不应该让用户的正常请求失败。这与"入队失败回滚并返回 503"（P04）形成对比——**同一项目里不同功能的可靠性等级不同，取决于它是不是业务主链路**。

**Q7. "资料完善"的六项是什么？**

**参考答案**：`nickname`、`gender`、`birthday`、`city`、`bio`，以及**至少一张 `approved` 的照片**（`missing_fields` 第 76–90 行）。六项齐全 → `complete`，否则 `incomplete`。
