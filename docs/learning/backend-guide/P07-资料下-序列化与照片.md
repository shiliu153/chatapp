## §2 读前必建概念

### 1）序列化器（Serializer）是"模型 ↔ JSON"的翻译层 + 校验层

- `ModelSerializer`：由 `Meta.model` + `fields` 自动生成字段，省事（本项目多数用它）
- 手写 `Serializer`：字段要一个个声明，适合"输入字段与模型字段不一致"的场景（本项目的 `ProfileUpdateSerializer` 就是——它要接 `tag_ids` 这种非模型字段）
- 方向：`序列化`（模型 → dict → JSON，读接口用）与 `反序列化 + 校验`（JSON → validated_data，写接口用）

### 2）两个校验钩子

| 钩子 | 何时用 | 例子 |
|---|---|---|
| `validate_<字段名>(self, value)` | 单字段规则 | `validate_birthday` 判未满 18 |
| `validate(self, attrs)` | 跨字段规则（要比较两个字段） | `PreferenceSerializer.validate` 比较 age_min/age_max |

### 3）`source=` 是字段映射

`user_id = serializers.IntegerField(source="user.id", read_only=True)`：输出的键叫 `user_id`，取值路径是 `profile.user.id`。**这是本项目最容易读错的一处**：`ProfileSerializer` 的 `id` 是 **profile 表主键**，`user_id` 才是账号 ID（第 42 行注释写明了）。

### 4）DRF 会在只读字段上"自动调用"取到的可调用对象

`missing_fields = serializers.ListField(...)` 没有 `source`，DRF 取值时会 `getattr(profile, "missing_fields")` 得到**绑定方法**，然后发现它可调用就顺手调用一次。所以模型上的 `def missing_fields(self)` 能直接被序列化输出。

### 5）`get_object_or_404(queryset, **条件)`

它把"查不到"自动变成 HTTP 404（抛 `NotFound`，走 P03 的异常处理器）。本项目有个关键用法：**用"当前用户自己的 queryset"当第一个参数**——这样天然防越权（删别人的照片会 404，而不是 403 泄露存在性）。

### 6）多部分表单（multipart）与文件字段

上传文件用 `multipart/form-data`，`ImageField` 会校验"是不是合法图片"（依赖 Pillow）。**字段名必须是 `file`**（`PhotoUploadSerializer` 第 105 行），这也是接口文档里写的 multipart 字段名。

## §4 动手实验

> 前置：先按 P05 实验 1 登录，拿到 `$login.access`。下面用 `$H = @{ Authorization = "Bearer $($login.access)" }` 简写。

### 实验 1 · 走一遍"从零到 complete"

```powershell
cd D:\pycharmproject\chat_app\chatapp
$H = @{ Authorization = "Bearer $($login.access)" }
# 1) 未完善
Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/users/me -Headers $H | ConvertTo-Json -Depth 5
# 预期 status=incomplete，missing_fields 列出 6 项
```
```powershell
# 2) 补齐文本字段（注意 birthday 格式）
$patch = @{ nickname = "小测"; gender = "female"; birthday = "2000-05-20"; city = "上海"; bio = "学习中" } | ConvertTo-Json
Invoke-RestMethod -Method Patch -Uri http://127.0.0.1:8000/api/v1/users/me -Headers $H -ContentType 'application/json' -Body $patch |
  Select-Object status, missing_fields
# 预期 status=incomplete, missing_fields=@("photos")
```
```powershell
# 3) 传一张图（先造一张 50x50 的小图）
python -c "from PIL import Image; Image.new('RGB',(50,50),(255,44,85)).save('test-photo.png')"
curl.exe -s -X POST http://127.0.0.1:8000/api/v1/users/me/photos -H "Authorization: Bearer $($login.access)" -F "file=@test-photo.png"
# 预期 201 + {id,url,status:"approved",order:0}（AUTO_APPROVE=1）
Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/users/me -Headers $H | Select-Object status, missing_fields
# 预期 status=complete, missing_fields=@()
```
> 顺手确认磁盘产物：`ls chatapp\media\photos\2026\10\`（`upload_to="photos/%Y/%m/"` 的落盘位置）。

### 实验 2 · 三个即时拒绝

```powershell
# a) 未满 18
Invoke-RestMethod -Method Patch -Uri http://127.0.0.1:8000/api/v1/users/me -Headers $H -ContentType 'application/json' -Body (@{ birthday = "2015-01-01" } | ConvertTo-Json)
# 预期 400 "未满 18 周岁,无法使用本应用"

# b) 无效标签
Invoke-RestMethod -Method Patch -Uri http://127.0.0.1:8000/api/v1/users/me -Headers $H -ContentType 'application/json' -Body (@{ tag_ids = @(999999) } | ConvertTo-Json)
# 预期 400 "存在无效的标签"

# c) 不存在的标签接口？先看标签池
Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/users/tags -Headers $H | ConvertTo-Json -Depth 3
```

### 实验 3 · 亲手看到"契约例外"（**本批最有价值的实验**）

```powershell
# 连传 7 张（第 7 张应被拒）
1..7 | ForEach-Object { curl.exe -s -X POST http://127.0.0.1:8000/api/v1/users/me/photos -H "Authorization: Bearer $($login.access)" -F "file=@test-photo.png"; "" }
```
**观察点**：第 7 次的响应是 `{"code":400,"message":"最多上传 6 张照片"}` —— **没有 `request_id`**。
再对比一次"正常失败"：
```powershell
curl.exe -i http://127.0.0.1:8000/api/v1/users/me   # 不带 token
# 预期 {"code":401,"message":"身份认证信息未提供。","request_id":"..."} —— 有 request_id
```
**结论**：凡是走 DRF 异常（抛异常）的失败都有 `request_id`；凡是视图里手写 `Response({...}, status=400)` 的都没有。这就是 `conventions.md` 第 60 行那条例外的机制性解释。

### 实验 4 · 越权与拉黑都不泄露存在性

```powershell
# 用别人的照片 id 删除（先随便试一个大 id）
curl.exe -i -X DELETE http://127.0.0.1:8000/api/v1/users/me/photos/999999 -H "Authorization: Bearer $($login.access)"
# 预期 404（不是 403）：从"我的照片"queryset 里查不到
# 看他人资料
Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/users/2 -Headers $H | ConvertTo-Json -Depth 5
# 预期只有 user_id/nickname/gender/age/city/bio/tags/photos —— 没有 phone/birthday/preference/missing_fields
```

### 实验 5 · 在线状态接口（配合 P06 实验 3）

```powershell
Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/presence?user_ids=1,2,1,999999" -Headers $H | ConvertTo-Json -Depth 5
```

## §5 自查题

**Q1. `GET /users/me` 里的 `id` 和 `user_id` 分别是什么？**

**参考答案**：`id` 是 **profile 表主键**，`user_id` 是账号（User）主键。`users/serializers.py` 第 42 行注释与 `CLAUDE.md` 都强调"对外标识用户一律用 `user_id`"。客户端若把 `id` 当用户 ID 用，数据会错位。

**Q2. 为什么 `ProfileUpdateSerializer` 用手写 Serializer 而不是 ModelSerializer？**

**参考答案**：它的输入集合与模型字段不一致——多了一个非模型的 `tag_ids`（多对多，需要单独 `set`），且要为昵称/简介/生日写专门校验（敏感词、年龄）。用 ModelSerializer 反而要大量覆写。

**Q3. `PreferenceSerializer.validate` 里为什么要 `getattr(self.instance, ...)`？**

**参考答案**：PATCH 是局部更新，客户端可能只传 `age_min`。此时 `age_max` 不在 `attrs` 里，必须从数据库现有对象（`self.instance`）取，否则跨字段比较会误判。

**Q4. 本册里有哪两处（含子项共四处）不遵守统一错误契约？为什么？**

**参考答案**：`upload_photo` 的数量超限（第 64 行）与 `presence_status` 的三处参数错误（第 90、94、98 行）。它们都在视图里直接 `return Response({"code":400,"message":...}, status=400)`，**绕过了 DRF 异常处理器**，因此缺少 `request_id`。文档已在 `conventions.md` 第 60 行把该字段声明为可选。

**Q5. 删除照片为什么用 `get_object_or_404(request.user.photos, ...)` 而不是先查 `Photo` 再比对 `user`？**

**参考答案**：直接把查询范围限定为"我自己的照片"，别人的照片等价于"不存在"→ 404。既省一次判断，又避免用 403 泄露"这个 id 存在但不属于你"。这与 P07 实验 4、以及 `errors.md` 里"被拉黑的人一律按不存在处理"是同一种防探测思路。

**Q6. `photo.file.delete(save=False)` 的 `save=False` 是什么意思？为什么必须有？**

**参考答案**：`FileField.delete()` 默认会在删除文件后**保存模型**；此时记录马上也要被删除（第 78 行），不需要再写一次数据库。传 `save=False` 只删磁盘文件，避免多余的 UPDATE。

**Q7. 照片过审为什么会改变"资料完善度"？**

**参考答案**：`missing_fields` 的第 6 项是"至少一张 `approved` 的照片"（P06 第 88–89 行）。所以照片被驳回/删除会让用户从 `complete` 掉回 `incomplete`，进而失去滑卡候选资格——`users/services.py` 第 20–22 行因此必须重算。
