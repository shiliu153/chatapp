## §2 读前必建概念：三个进程

| 进程 | 本机形态 | 负责 | 它挂了会怎样 |
|---|---|---|---|
| **MySQL** | Windows 服务 `MySQL80`，端口 3306 | 业务数据的唯一持久层（用户、滑卡、配对、动态…） | 一切接口 500；`readyz` 报 `db: fail` |
| **Redis** | Docker 容器 `chatapp-redis`，端口 6379 | ①验证码缓存（DB0）②限流计数（DB0）③Celery 队列（DB1）④测试缓存（DB15）/测试队列（DB14） | 短信验证码发不出、限流失效、`readyz` 报 `redis: fail`、**测试直接红** |
| **Django** | `manage.py runserver`，端口 8000 | 处理 HTTP 请求 | 接口全不可达 |
| （Celery worker） | 本批**不起**，P10 才用 | 消费队列、调腾讯云 IM | 消息能发但对方收不到 IM 通知 |

关键：**Redis 是"临时数据 + 队列"，MySQL 是"正经数据"**。所以测试时 MySQL 用独立的 `test_chatapp_dev`（跑完自动销毁），Redis 用 DB15/DB14（与开发的 DB0/DB1 隔离）。

## §4 动手实验

### 步骤 1 · 起 Docker 引擎（Redis 的宿主）

```powershell
docker info --format '{{.ServerVersion}}'
```
- 若报 `error during connect ... Access is denied` 或 `cannot find the file`：**Docker Desktop 没运行**，从开始菜单启动它，等托盘鲸鱼图标变绿（首次可能 30–60 秒）。
- 成功输出形如：`28.3.2`

### 步骤 2 · 起 Redis

```powershell
cd D:\pycharmproject\chat_app\chatapp
docker compose -f docker-compose.dev.yml up -d
docker compose -f docker-compose.dev.yml ps
docker exec chatapp-redis redis-cli ping
```
预期：容器 `chatapp-redis` 状态 `Up`，端口映射 `0.0.0.0:6379->6379/tcp`；最后一行输出 **`PONG`**。

> 括注：`docker-compose.dev.yml` 只有 12 行——一个 `redis:7-alpine` 服务 + 一个具名卷。**这个文件值得自己读一遍**，你就懂"容器化"在这个项目里到底用了多少。

### 步骤 3 · 进 Python 环境

```powershell
conda activate Django
python -c "import sys, django; print(sys.version.split()[0], django.get_version())"
```
预期：`3.10.19 5.2.9`

### 步骤 4 · 配置自检

```powershell
python manage.py check
```
预期：`System check identified no issues (0 silenced).`
- 若报数据库连接错误：检查 `chatapp/.env` 是否存在（模板见 `.env.example`，缺失就复制一份并填口令）。

### 步骤 5 · 建表

```powershell
python manage.py migrate
python manage.py showmigrations --plan | Select-String '\[ \]'
```
预期：`No migrations to apply.`；第二条命令**应当没有任何输出**（没有未应用的迁移）。
> 括注：`migrate` 把各 app 的 `migrations/*.py` 同步到 MySQL 表结构。P06 会精读这套机制。

### 步骤 6 · 起服务器并打两个探针

开一个终端：
```powershell
python manage.py runserver 127.0.0.1:8000
```
另开一个终端（**这一步是 P03 的伏笔，注意响应头**）：
```powershell
$r = Invoke-WebRequest http://127.0.0.1:8000/api/v1/health -UseBasicParsing
$r.StatusCode; $r.Content; $r.Headers['X-Request-Id']
$r2 = Invoke-WebRequest http://127.0.0.1:8000/api/v1/readyz -UseBasicParsing
$r2.Content
```
实测预期：
```
200
{"status":"ok"}
e85b0c01d4da4246a7c5972fe941ea94          <- 每次请求都不一样
{"status":"ok","checks":{"db":"ok","redis":"ok"}}
```
同时**服务器那个终端**会打出：
```
INFO 2026-10-09 18:32:56,260 [e85b0c01d4da4246a7c5972fe941ea94] chatapp.request GET /api/v1/health -> 200 15ms
```
> **观察点（重要）**：日志里的 `[...]` 和响应头 `X-Request-Id` 是**同一个值**。这就是"一个请求可以被端到端对账"的机制，实现在 `config/middleware.py`(33 行) —— P03 的主角。

### 步骤 7 · 跑测试（建立绿色基线）

```powershell
$env:PYTHONIOENCODING = 'utf-8'; $env:PYTHONUTF8 = '1'   # 防中文乱码
python manage.py test accounts --noinput
python manage.py test --noinput
```
实测预期：
```
Ran 40 tests in 1.690s
OK
...
Ran 337 tests in 26.451s
OK
```
- `--noinput`：自动丢弃已存在的旧测试库，不交互提问。**脚本里必须加**。
- 若看到 `Type 'yes' if you would like to try deleting the test database 'test_chatapp_dev'` 后面跟着 `EOFError`：你（或上一个进程）留下了脏测试库，加上 `--noinput` 重跑即可。
- 若日志里出现 `Traceback` 但结果是 `OK`：**正常**。测试故意用 `unittest.mock` 把 db/redis 探针替换成抛异常，来断言降级路径（503）。判断成败看 `Ran ... OK` 与退出码，不要看红字。

## §5 自查题（先自己答，再看答案）

**Q1. 为什么跑测试必须先把 Redis 起来？**

> 提示：看 `chatapp/.env.example` 第 18–21 行、[../../pitfalls/testing.md](../../pitfalls/testing.md) 第 7 行。

**参考答案**：Redis 在本项目承担三类"测试会碰到"的职责：①验证码缓存 ②**限流计数**（限流用例要 `cache.clear()`，清的就是 Redis）③**Celery broker**（测试要断言"任务入队了什么"，broker 不通入队即失败，业务代码会走 503 降级分支）。所以 Redis 缺席不是"少测一点"，而是**一批用例直接变红或断言错位**。MySQL 那边用的是独立测试库 `test_chatapp_dev`，与 Redis 的 DB15/DB14 是两码事。

**Q2. `test_chatapp_dev` 和 Redis 的 DB15/DB14 有什么区别？**
**参考答案**：前者是 Django 测试运行器**自动创建、跑完销毁**的 MySQL 库（表结构来自 migrations，数据来自测试用例）；后者是 Redis 的逻辑库编号（同一个 Redis 实例里用编号隔离 key 空间），测试固定用 15 存缓存、14 当队列，**这样清缓存/清队列不会碰到开发环境的 DB0/DB1**。

**Q3. 现在你机器上，"Redis 停了"会造成哪三个可观察现象？**
**参考答案**：①`GET /api/v1/readyz` 返回 503 且 `checks.redis` 非 ok；②`POST /auth/sms/send` 无法写验证码/入队，返回 503；③`python manage.py test` 大面积红。
