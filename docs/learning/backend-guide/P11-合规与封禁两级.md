## §2 读前必建概念

### 1）DRF 权限类怎么工作

`permission_classes` 里的每个类实现 `has_permission(request, view)`：
- 返回 `True` → 放行
- 返回 `False` → DRF 抛 `PermissionDenied`（403）
- **抛 `PermissionDenied("自定义文案")`** → 同样是 403，但 `message` 是中文定制文案（本项目用这种，因为要给人看）

`settings.REST_FRAMEWORK["DEFAULT_PERMISSION_CLASSES"]` 是**全局默认**（P02 第 213–216 行）：
```python
("rest_framework.permissions.IsAuthenticated", "moderation.permissions.IsNotHeavyBanned")
```
所以**每一个新接口自动继承这两条**——这是"全局类"相对"每视图写一遍"的核心优势：**不会漏**。

### 2）白名单为什么用 `(method, path)` 而不是视图名

```python
BAN_EXEMPT = {("GET", "/api/v1/users/me"), ("GET", "/api/v1/users/tags")}
```
权限类只能拿到 `request.method` 与 `request.path`，拿不到"视图函数名"（那需要额外解析 URL）。用 `(方法, 路径)` 最直白。**代价**：路径写死，改路由必须同步改这里（这是一处**隐性耦合**，值得记进笔记）。

为什么是这两个？
- `GET /users/me`：被封禁的人必须能看到自己的 `status` 与 `ban_reason`（前端要展示封禁原因）
- `GET /users/tags`：标签池是公共字典数据，不涉及社交行为

### 3）DRF 的"未认证"与"无权限"是两件事

`IsNotHeavyBanned.has_permission` 第 18–19 行：**未认证直接返回 True**。为什么？因为认证失败会由认证类/`IsAuthenticated` 先返回 401；权限类不该把"没登录"误判成"被封禁"。分工：
- 认证类（`SessionJwtAuthentication`）→ 令牌无效/被顶 → 401
- `IsAuthenticated` → 没登录 → 401/403
- `IsNotHeavyBanned` → 已登录但重封禁 → 403

### 4）拉黑的"对称不可见"

`blocked_user_ids(user)` 返回 **我拉黑的 ∪ 拉黑我的**。于是：
- 我拉黑了对方 → 我看不到对方
- 对方拉黑了我 → 我也看不到对方（**这是关键**：单向拉黑也导致双向不可见）
- 对外统一表现成"**用户不存在**"（404），而不是 403——避免"探测某人是否拉黑了我"（`docs/api/errors.md` 第 12 行）

## §4 动手实验

> 前置：`$H` = 你自己的 access（P05）；`$B` = 另一个账号的 access（可用 `seed_fake_users` 造出来的账号，或第二个手机号登录）。

### 实验 1 · 举报的幂等

```powershell
$body = @{ target_user_id = 8; type = "harassment"; detail = "测试举报" } | ConvertTo-Json
curl.exe -i -s -X POST http://127.0.0.1:8000/api/v1/reports -H "Authorization: Bearer $($login.access)" -H "Content-Type: application/json" -d $body | Select-String 'HTTP/|code'
# 第二次完全相同 → 应返回 200 且 id 相同（不是 201）
curl.exe -i -s -X POST http://127.0.0.1:8000/api/v1/reports -H "Authorization: Bearer $($login.access)" -H "Content-Type: application/json" -d $body | Select-String 'HTTP/|code'
# 举报自己 → 400 "不能举报自己"
```
> 注意 `curl.exe` 在 PowerShell 里 `-d` 传 JSON 需要转义引号；若嫌麻烦就用 `Invoke-RestMethod`（见 P07 的写法）。

### 实验 2 · 拉黑导致"双向不可见"

```powershell
# 拉黑 8 号
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/blocks -Headers $H -ContentType 'application/json' -Body (@{ target_user_id = 8 } | ConvertTo-Json)
# 1) 他人资料 → 404（不是 403）
curl.exe -i -s http://127.0.0.1:8000/api/v1/users/8 -H "Authorization: Bearer $($login.access)" | Select-String 'HTTP/'
# 2) 在线状态里被省略
Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/presence?user_ids=8" -Headers $H | ConvertTo-Json
# 预期 results 里没有 8 号
# 3) 候选卡里不出现
Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/discovery/candidates?limit=20" -Headers $H |
  Select-Object -ExpandProperty user_id
# 4) 拉黑列表
Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/blocks -Headers $H | ConvertTo-Json -Depth 5
# 5) 解除 → 204,再查资料应恢复可见
Invoke-RestMethod -Method Delete -Uri http://127.0.0.1:8000/api/v1/blocks/8 -Headers $H
```
（若起了 worker，还能在 worker 日志里看到 `blacklist_add` / `blacklist_remove` 任务——那是 `sync_im_blacklist` 入队的。）

### 实验 3 · **重封禁 = 全站 403 + 白名单可通**（本批核心实验）

## §5 自查题

**Q1. 为什么封禁要做成全局权限类，而不是在每个视图里检查？**

**参考答案**：全站 403 是**横切关注点**，涉及所有接口。放在 `DEFAULT_PERMISSION_CLASSES` 里，新接口自动继承，**不可能漏**；逐视图写则必然有遗漏（新人加接口时最容易忘）。代价是每个请求多一次 `get_profile`（第 22 行）与"路径写死在白名单里"的隐性耦合。

**Q2. 白名单为什么只有 `GET /users/me` 与 `GET /users/tags`？**

**参考答案**：被封禁的人**必须**能看到自己的资料（前端要展示 `status` 与 `ban_reason`）以及公共标签池；其余接口（滑卡、广场、聊天相关、看他人资料）都该被拦住。

**Q3. `IsNotHeavyBanned` 里为什么"未认证返回 True"？**

**参考答案**：职责分离。未认证应由认证类与 `IsAuthenticated` 处理（返回 401）；如果这里返回 False，会得到一个含义错误的 403，把"没登录"说成"被封禁"。

**Q4. 举报接口怎么做到幂等？对同一对象反复举报会发生什么？**

**参考答案**：`Report.objects.get_or_create(reporter=..., target=..., status=PENDING, defaults={...})`——只要还有**未处理**的举报，就不再新建，直接返回已有记录（HTTP 200 而非 201）。已处理之后再举报会新建一条（这是合理的：处理完还能再犯）。

**Q5. 拉黑为什么是"双向不可见"，而不是"单向屏蔽"？**

**参考答案**：`blocked_user_ids` 取"我拉黑的 ∪ 拉黑我的"（services 第 15–17 行）。这样被拉黑者也无法通过候选卡/资料卡/在线状态看到拉黑者，避免纠缠；对外统一 404 而非 403，防止探测"谁拉黑了我"。

**Q6. `_write_log` 里为什么敢 try/except 吞掉异常，而 `sms_send` 的入队失败必须 fail-closed？**

**参考答案**：等级不同。审计日志是**旁路信息**，写失败不该破坏运营的主操作（Profile 已保存）；而短信入队失败会让用户**陷入无法重试的死状态**，必须回滚并明确报错。判断标准：**失败会不会让用户卡住/数据不一致**。

**Q7. `BanLog` 为什么在 admin 里做成只读？**

**参考答案**：审计记录的价值在于"不可篡改"。`has_add/change/delete_permission` 全返回 False，运营只能看不能改；当前生效状态在 `Profile.status`/`ban_reason` 上，历史在 `BanLog` 里——**状态与历史分离**。
