## §2 读前必建概念

### 1）"门禁（gate）"是什么

一个会在 CI/测试里失败、从而**阻止你合并代码**的自动检查。本项目有两条硬门禁：
- 后端全量测试绿（`python manage.py test`）
- `flutter analyze` 零告警

本批讲的 `ApiDocsCoverageTests` 是第一条里的一个具体门禁：**接口与文档必须一一对应**。

### 2）双向比对

| 方向 | 含义 | 报错文案 |
|---|---|---|
| URLconf 有、文档没有 | 新加了接口没写文档 | "接口 X 未写文档，请补到 docs/api/…" |
| 文档有、URLconf 没有 | 接口删了/改名了，文档残留 | "文档记录的 X 在 URLconf 中已不存在…" |

单向检查（只查第一种）会漏掉"文档说谎"的情况，双向才能保证文档**永远与代码一致**。

### 3）测试策略：三层

| 层 | 例子 | 特点 |
|---|---|---|
| 纯逻辑单测（`SimpleTestCase`） | `api_doc_coverage` 的正则、userSig 公式、request_id 注入函数 | 不碰数据库、毫秒级 |
| 视图/接口测试（`APITestCase`） | 几乎所有业务用例 | 走 HTTP 边界、用真实 URL 与序列化器 |
| 任务测试（`TestCase` + `task.run()`） | `im/tests.py` 的任务用例 | 直接调任务体、mock 外部客户端 |

### 4. 测试写法归纳（横扫任务 3）

```powershell
python manage.py test --noinput -v 2 | Select-String "ok$"
```
把 9 个 `tests.py` 横向扫一遍，归纳出本项目的测试惯例：
1. **从 HTTP 边界进**：用 `APITestCase` + `self.client.post(...)`，不 mock 自己的视图/序列化器。
2. **外部系统一律 mock**：`patch("im.tasks.xxx.delay")`、`patch("im.client.*")`（腾讯一次都不能真打——`docs/pitfalls/testing.md` 第 9–10 条）。
3. **`on_commit` 要用 `captureOnCommitCallbacks(execute=True)` 包住**（testing.md 第 8 条），否则断言永远不触发。
4. **任务体直接 `task.run(...)`** 测，不走 broker。
5. **限流用例先 `cache.clear()`**（计数在 Redis，跨用例会残留——testing.md 第 11 条）。
6. **纯逻辑单独测**（日期换算、签名公式、正则），用 `SimpleTestCase` 跑得快。
7. **失败路径必须有专门用例**（几乎每个外部调用都有 `test_*_network_error_returns_false`）。
8. **测试名就是文档**：`test_import_failure_raises_so_celery_retries`、`test_pending_kick_runs_before_issuing_sig`、`test_heavy_banned_rejected`——读名字就知道它在保护什么。

## §5 自查题（本批是全书总复盘）

**Q1. 一个请求从进来到出去，完整经过哪些组件？**

**参考答案**：WSGI 服务器 → `RequestIdMiddleware`（生成/回显追踪 ID）→ Security/CORS/Session/Common/CSRF/Auth/Message/XFrame → URLconf（`config.urls` → `config.api_urls` → app `urls.py`）→ DRF 视图（认证类 → 权限类 → 限流器）→ 视图/序列化器/service → ORM（MySQL）→ 需要异步副作用则入队（Redis broker）→ 响应 → DRF 异常处理器（失败时统一信封）→ 中间件回程（写 `X-Request-Id`）。

**Q2. 这个项目里"必须成对出现"的改动有哪些？**

**参考答案**：①接口 ↔ `docs/api/` 文档（门禁强制）；②模型 ↔ migrations；③状态变更 ↔ `BanLog` 审计 + IM 系统通知；④数据库提交 ↔ 入队（`on_commit`）；⑤`.env.example` 新增键 ↔ settings 读取点；⑥前端契约常量 ↔ 后端常量（如 `system_notice` 相关，`CLAUDE.md` 特别提醒"两边别单改"）。

**Q3. 项目里"跨系统副作用"为什么全部走 Celery？有没有例外？**

**参考答案**：因为响应路径同步调外部会让用户等待、失败无法重试、抖动会污染业务结果。**例外是 `POST /im/user_sig`**（P09）：客户端必须立刻拿到 userSig，省不掉；作者用"标记 + 幂等建号 + 失败不写标记"把风险压到最低。

**Q4. 项目里的"幂等"出现在哪些地方？各用什么手段？**

**参考答案**：滑卡（`get_or_create` + 唯一约束）、配对（`pair_kwargs` + 唯一约束 + `created` 才通知）、举报（按 `status=PENDING` 的 `get_or_create`）、点赞（唯一约束 + `get_or_create`）、拉黑（`get_or_create` + 删除不报错）、登录（60 秒重放窗口）、IM 建号（7015 视为成功）、`kick_pending`（标记存在才踢）。

**Q5. 项目里"什么错误可以吞、什么必须抛"的判据是什么？**

**参考答案**：**看失败会不会让用户卡死或数据不一致**。可以吞：presence 写入（点缀）、审计写失败（旁路）、IM client 层（返回 False，由 tasks 决定重试）。必须抛/必须回滚：短信入队失败（否则用户被 60 秒占位卡死，fail-closed → 50301）、任务失败（否则重试不发生）、所有可预期的参数/权限错误（转成 DRF 异常以保持信封）。

**Q6. 为什么说"文档门禁"和"数据库唯一约束""全局权限类"是同一种思路？**

**参考答案**：三者都是**把重要约束交给不会疲倦的机制**：唯一约束防并发重复插入、全局权限类防新接口漏加封禁检查、文档门禁防文档腐烂。人的自觉不可靠，机制可靠——**这是本项目最值得复制的工程习惯**。
