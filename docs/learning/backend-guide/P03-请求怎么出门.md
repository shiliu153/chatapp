## §1 本批目标

1. 说出一次请求穿过中间件时，**谁先执行、谁后执行**，以及为什么 `RequestIdMiddleware` 必须排第一；
2. 说出失败响应的三个字段从哪来，业务码什么时候等于 HTTP 状态码、什么时候不等于；
3. 说出**未捕获异常**为什么不遵守错误契约——以及这个事实对写业务代码的约束。

## §2 读前必建概念

### 1）中间件是"洋葱"，不是"链"

`MIDDLEWARE` 列表里的顺序 = 请求阶段的**进入顺序**，响应阶段的**退出顺序正好相反**：

```
请求 →  RequestIdMiddleware → Security → CORS → Session → Common → CSRF → Auth → Message → XFrame → 视图
响应 ←  RequestIdMiddleware ← Security ← CORS ← Session ← Common ← CSRF ← Auth ← Message ← XFrame ← 视图
```

所以放在**第 1 位**的 `RequestIdMiddleware`：
- 请求阶段最先跑 → 后面所有环节的日志都已经有 `request_id` 可用；
- 响应阶段最后跑 → 它能确保**最终**响应头一定带上 `X-Request-Id`；
- 它的 `finally` 在整条链结束后才执行 → 用来清理上下文变量。

### 2）`contextvars` 解决什么

一个 worker 进程会同时处理多个请求（线程或协程）。"当前请求的 id"是**每个请求私有的临时状态**。用全局变量会被并发覆盖；用 `threading.local` 在协程下又不够。`contextvars.ContextVar` 是官方给的"随执行上下文传播的局部变量"。

### 3）DRF 的异常处理器（`EXCEPTION_HANDLER`）是唯一收口点

DRF 把视图里抛出的 `APIException` 子类（`ValidationError`、`NotAuthenticated`、`PermissionDenied`、`Throttled`…）交给 settings 第 217 行指定的 `config.exceptions.api_exception_handler` 处理。**所有"预期内"的失败都必须变成 DRF 异常**，才能被收口成统一形状。

### 4）错误契约（全项目强制）

- 成功：HTTP 2xx + 资源 JSON
- 失败：`{"code": <int>, "message": "<中文>", "request_id": "<hex|->"}`
- `code` 规则：前 3 位与 HTTP 状态码一致，后 2 位是业务序号；**没有专属业务码时，`code` 就等于 HTTP 状态码**（例：401、404）

`docs/api/conventions.md` 第 60 行还有一条**例外**要记住：少数接口在视图内直接校验失败时只返回 `code` + `message`，**不含 `request_id`**（目前是「在线状态参数错误」与「照片超过 6 张」两处），客户端要把该字段当可选。

## §3 精读清单

### 1. `config/middleware.py`（33 行）

| 行 | 在干什么 | 要抓的点 |
|---|---|---|
| 14–16 | `__init__(self, get_response)` | Django 中间件的两种写法之一（旧式 `MiddlewareMixin`）；`get_response` 就是"下一层" |
| 19 | `request_id = request.headers.get("X-Request-Id") or uuid.uuid4().hex` | **尊重客户端传入的 id**，没有才生成。这就是 `conventions.md` 第 22 行的"请求头可带 X-Request-Id" |
| 20 | `request.request_id = request_id` | 挂到 request 上，视图里可直接用 |
| 21 | `set_request_id(request_id)` | 写进 contextvar，供日志 Filter 读取 |
| 22 | `start = time.monotonic()` | 用单调时钟测耗时（不受系统时间调整影响） |
| 24 | `response = self.get_response(request)` | **真正的视图调用发生在这里** |
| 25–27 | 算耗时；`level = WARNING if duration_ms >= settings.REQUEST_SLOW_MS else INFO` | 慢请求阈值来自 settings 第 249 行（默认 500ms） |
| 28–29 | `logger.log(level, "%s %s -> %s %.0fms", method, path, status, duration)` | 你在 P00 见过的那行日志 |
| 30 | `response["X-Request-Id"] = request_id` | 回填响应头 |
| 32–33 | `finally: set_request_id(None)` | **必须清理**：worker 会复用执行上下文，不清理会污染后续请求 |

### 2. `config/request_id.py`（22 行）

| 行 | 在干什么 |
|---|---|
| 6 | `_request_id = contextvars.ContextVar("request_id", default=None)` |
| 9–10 | `set_request_id(value)` |
| 13–14 | `current_request_id()` —— `config/exceptions.py` 第 34 行用它填 `request_id` 字段 |
| 17–22 | `RequestIdFilter(logging.Filter)`：**每条日志记录**都被塞上 `record.request_id = current_request_id() or "-"` |

> `"-"` 这个兜底很重要：Celery worker 里没有 HTTP 请求，日志会显示 `[-]`，一眼就能区分"这条日志来自请求"还是"来自任务"。

### 3. `config/exceptions.py`（36 行）

| 行 | 在干什么 | 要抓的点 |
|---|---|---|
| 6–22 | `_first_message(data)` 递归取第一条可读信息 | DRF 的错误数据形状五花八门（`{"detail": ...}`、`{"field": ["..."]}`、`[{...}]`），递归是为了**总能给用户一句话**；兜底文案 `"请求无效"` |
| 25–28 | `response = exception_handler(exc, context)`；`if response is None: return None` | **关键**：DRF 自己的处理器只认 `APIException`；遇到别的异常它返回 `None`，我们跟着返回 `None` → 异常继续往上抛给 Django → HTML 500 页。这就是"契约的边界" |
| 30 | `detail_code = getattr(exc, "detail_code", None)` | **异常可以自带业务码**：P05 的 `40101` 就是靠这个属性透传 |
| 31–35 | 重组 `response.data = {"code", "message", "request_id"}` | 契约的唯一实现处 |

### 4. `config/error_codes.py`（8 行）

六个业务码**全在 accounts 域**（P04/P05 会逐个用上）：`40101` 单设备冲突、`40001` 验证码过期、`40002` 验证码错误、`42901` 重发太频繁、`42902` 错误次数过多、`50301` 短信服务不可用。

> 想一个问题：为什么**别的域**（滑卡、举报、广场）没有专属业务码？（答案：它们用 HTTP 状态码 + `message` 就足够客户端分支；`code` 的价值在于"同一个 HTTP 状态码下要区分多种业务原因"，如 429 下的 42901/42902。）

### 5. `config/pagination.py`（8 行）

`LimitOffsetPagination` 子类，`default_limit = 20`、`max_limit = 100`。响应形状 `count/next/previous/results`（见 `conventions.md` §分页约定）。**它就是 settings 第 218 行那个 `DEFAULT_PAGINATION_CLASS`。**

### 6. 回看 settings 三处

- 第 254–256 行：`RequestIdFilter` 注册与 `%(request_id)s` 格式
- 第 217 行：`EXCEPTION_HANDLER` 注册
- 第 218 行：`DEFAULT_PAGINATION_CLASS` 注册

## §4 动手实验

### 实验 1 · 亲眼看契约与"契约失效"

```powershell
cd D:\pycharmproject\chat_app\chatapp
$code = @'
import os, django
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")
django.setup()
from django.test import Client, override_settings
plain = {
    "DEFAULT_AUTHENTICATION_CLASSES": ("accounts.authentication.SessionJwtAuthentication",),
    "DEFAULT_PERMISSION_CLASSES": ("rest_framework.permissions.IsAuthenticated",),
}
r1 = Client(SERVER_NAME="127.0.0.1").get("/api/v1/users/me")
print("带自定义处理器  :", r1.status_code, r1.content.decode())
with override_settings(REST_FRAMEWORK=plain):
    r2 = Client(SERVER_NAME="127.0.0.1").get("/api/v1/users/me")
    print("不带自定义处理器:", r2.status_code, r2.content.decode())
'@
$code | python -
```
**本机实测输出**：
```
带自定义处理器  : 401 {"code":401,"message":"身份认证信息未提供。","request_id":"138a63e028524a7fb6a74e4f09a1e7b8"}
不带自定义处理器: 401 {"detail":"身份认证信息未提供。"}
```
> 结论：`{code, message, request_id}` **不是 DRF 自带的**，是本项目 `config/exceptions.py` 加上的。这也解释了为什么"改接口不改文档"会让 `ApiDocsCoverageTests` 变红——契约是被测试盯住的（P14）。

### 实验 2 · 让慢请求日志升到 WARNING

把 settings 第 249 行改成 `REQUEST_SLOW_MS = 0`，起服务器请求 `/api/v1/health`，观察服务器日志 `INFO` → `WARNING`（`middleware.py` 第 27 行的分支）。改回 `500`。

### 实验 3 · 制造一个"契约外"的 500

在 P01 实验加的 `ping` 视图里写 `raise RuntimeError("boom")`，用 `curl.exe -i` 请求：
- `DEBUG=1`：返回 HTML 调试页（含堆栈），**不是** JSON 契约；
- 把 `DEBUG` 改 0：返回 Django 的 500 HTML。
**记住这个事实**：未捕获异常绕过 DRF 异常处理器。所以业务代码的纪律是——**任何可预期错误都转成 DRF 异常；调用外部系统的地方（IM、短信）一律吞异常并降级**（P09 会看到 `im/client.py` 的"永不抛异常"约定）。

### 实验 4 · 验证 request_id 端到端

起服务器后：
```powershell
$r = Invoke-WebRequest http://127.0.0.1:8000/api/v1/health -UseBasicParsing
$rid = $r.Headers['X-Request-Id']
$rid
```
拿这个值去服务器终端里 `Ctrl+F`，应该能定位到**该请求的日志行**（本项目同一请求目前只有一行访问日志，但它带着 `[...]` 前缀；P10 里 Celery 任务日志也会带同一个 id）。另试一次：请求时手动带上 header
```powershell
Invoke-WebRequest http://127.0.0.1:8000/api/v1/health -Headers @{'X-Request-Id'='my-trace-001'} -UseBasicParsing |
  Select-Object -ExpandProperty Headers
```
预期响应头回填的就是 `my-trace-001`（`middleware.py` 第 19 行的 `or`）。

## §5 自查题

**Q1. 为什么 `RequestIdMiddleware` 必须放在 `MIDDLEWARE` 第 1 位？**

**参考答案**：三个理由。①请求阶段最先执行，后续所有环节的日志都能带上 `request_id`；②响应阶段最后执行，能保证最终响应头带上 `X-Request-Id`（哪怕后面某层改过 response）；③`finally` 在整条链结束后执行，正好用来清理 contextvar。

**Q2. `finally: set_request_id(None)` 不写会怎样？**

**参考答案**：执行上下文（线程/协程）会被 worker 复用；残留的 id 会让**下一个请求的日志挂上上一个请求的 id**，端到端对账就失真了。这是"临时状态必须清理"的典型案例。

**Q3. `code` 什么时候等于 HTTP 状态码，什么时候不等于？**

**参考答案**：按 `error_codes.py` 的规则，无专属业务码时 `code = HTTP 状态码`（如 401、404、400）；有专属业务码时用专属码（如 429 下的 `42901`、401 下的 `40101`），实现方式是异常对象带 `detail_code` 属性（`exceptions.py` 第 30 行透传）。

**Q4. 未捕获的 `RuntimeError` 返回什么？这个事实对写代码有什么硬约束？**

**参考答案**：返回 Django 的 HTML 错误页（DEBUG 下是调试页），**不遵守** `{code,message,request_id}` 契约，因为 DRF 自己的 `exception_handler` 对非 `APIException` 返回 `None`，我们的处理器跟着 `return None`（`exceptions.py` 第 27–28 行）。约束：可预期错误必须转成 DRF 异常；跨系统调用必须自己吞异常降级，绝不让第三方故障穿透成 500。

**Q5. 分页响应的键与默认值/上限？**

**参考答案**：`count` / `next` / `previous` / `results`；默认 `limit=20`，上限 100（`config/pagination.py` 第 7–8 行）。

**Q6. `request_id` 字段会不会缺失？**

**参考答案**：会。`conventions.md` 第 60 行明确列出例外：视图内直接校验失败的两处（在线状态参数错误、照片超过 6 张）只返回 `code` + `message`。解析方必须把它当可选字段。
