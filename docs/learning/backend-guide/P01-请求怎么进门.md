## §2 读前必建概念

### 1）WSGI / ASGI 是什么

Python Web 服务器（`runserver`、`gunicorn`、uWSGI）不会自己懂 Django。它俩之间需要一个**约定接口**：服务器把 HTTP 请求翻译成 `environ` 字典 + `start_response` 回调交给应用，应用返回字节流。这就是 **WSGI**（同步）与 **ASGI**（异步，支持 WebSocket/长连接）。

本项目只启用 WSGI，依据是 `config/settings.py`：
- 第 92 行 `WSGI_APPLICATION = "config.wsgi.application"` ✅ 生效
- **没有** `ASGI_APPLICATION` 这一项 → `config/asgi.py` 是 `startproject` 生成的脚手架，没被使用
- 部署用 gunicorn（`requirements.txt` 末行），也是 WSGI

> 为什么不需要 ASGI？聊天消息走**腾讯云 IM SDK**（客户端直连腾讯），Django 只做业务数据与 IM 管理端调用，不承担长连接。

### 2）URLconf 是"有序列表 + 首次匹配即返回"

不是字典查找，也**不是最长匹配**：Django 拿着 `urlpatterns` 从上往下试，第一个 `path()` 匹配成功就调用对应视图，后面的**完全不看**。

### 3）`include()` 做的是"前缀剥离 + 下级解析"

```python
path("users/", include("users.urls"))     # config/api_urls.py:11
```
请求 `/api/v1/users/me` → `config/urls.py` 匹配 `api/v1/` → 传给 `config/api_urls.py` 的剩余部分是 `users/me` → 匹配 `users/`，剥离后剩余 `me` → 交给 `users/urls.py`，它第 6 行 `path("me", views.me)` 命中 → 调用 `users.views.me`。

### 4）末尾斜杠：本项目路径**全都不带**

`django.middleware.common.CommonMiddleware`（settings 第 67 行）默认 `APPEND_SLASH=True`，但它的逻辑是**单向**的：请求没有尾斜杠且匹配失败时，才尝试"补一个斜杠再匹配"。请求**带**尾斜杠而匹配失败，它不会帮你"去掉斜杠"。

实测（2026-10-09，`django.test.Client`）：

| 请求路径 | 状态码 |
|---|---|
| `/api/v1/health` | **200** |
| `/api/v1/health/` | **404** ❗ |
| `/api/v1/users/me` | 401（未带令牌） |
| `/api/v1/posts` | 401（路由存在，只是要鉴权） |
| `/api/v1/nope` | 404 |

**结论：写客户端/curl 时路径一律不加尾斜杠。**

### 5）视图有两种形态

- 函数视图：本项目 API 全是这种，外面套了 DRF 的 `@api_view`（例：`accounts/views.py` 第 26 行 `@api_view(["GET"])`）
- 类视图：需要 `.as_view()`（例：`accounts/urls.py` 第 8 行 `views.SessionTokenRefreshView.as_view()`）

### 2. `config/__init__.py`（7 行）——**两行都别跳过**

| 行 | 在干什么 |
|---|---|
| 3 | `pymysql.install_as_MySQLdb()`——用纯 Python 的 PyMySQL 顶替需要编译 C 扩展的 `mysqlclient`（Windows 上省去编译麻烦） |
| 5 | `from .celery import app as celery_app`——**导入 `config` 包就等于加载 Celery 应用**（P10 伏笔：所以 `runserver` 进程里也有 Celery app 对象，只是没有 worker 去消费） |
| 7 | `__all__ = ("celery_app",)`——声明对外只暴露这个 |

### 3. `config/wsgi.py` / `config/asgi.py`（各 16 行）

结构完全相同，只有最后一行不同：`application = get_wsgi_application()` / `get_asgi_application()`。**注意 settings 只引用了前者**。

### 4. `config/urls.py`（15 行）——三条顶层入口

| 行 | 入口 | 服务谁 |
|---|---|---|
| 9 | `admin/` | Django 自带后台（超级用户用） |
| 10 | `api/v1/` → `config.api_urls` | **App 与 Web 端调用的全部业务接口** |
| 11 | `ops/` → `ops.urls` | 自研运营后台（P13，服务端渲染 HTML） |
| 14–15 | `if settings.DEBUG:` 才挂 `static(MEDIA_URL, ...)` | 开发期由 Django 直接发上传的图片；生产交给 nginx（见 settings 第 195 行注释） |

### 5. `config/api_urls.py`（18 行）——业务路由总表

| 行 | 内容 |
|---|---|
| 8–9 | `health`、`readyz` —— 实现在 `accounts/views.py` 第 26–59 行（**探针为什么放在 accounts？** 因为它是最早的 app，临时落脚；读 P04 时注意这个"历史遗留"） |
| 10 | `auth/` → `accounts.urls` |
| 11 | `users/` → `users.urls` |
| 12 | `im/` → `im.urls` |
| 13 | `discovery/` → `discovery.urls` |
| 14 | `""` → `moderation.urls`（**空前缀**：它的模式是 `reports` / `blocks`，直接挂在 `/api/v1/` 下） |
| 15 | `""` → `feed.urls`（同上：`posts` 系列） |
| 16 | `matches` → `discovery_views.match_list`（**为什么不放进 discovery/urls.py？** 因为对外路径是 `/api/v1/matches` 而不是 `/api/v1/discovery/matches`，是为客户端方便） |
| 17 | `presence` → `users_views.presence_status`（同理，挂在根上） |

⚠️ **顺序陷阱**：第 14–15 行的空前缀 include 放在第 16–17 行具体路径**之前**。当前之所以安全，是因为所有模式都是精确字面量，没有互相包含。**你以后新增接口时，必须自己确认这一点**——这不是机制保证的，是当前事实。

### 6. 六个 app 的 `urls.py`（9/9/8/7/12/34 行）

建议**并排一次性读完**，建立"接口 → 函数"总表：

| 文件 | 路由 |
|---|---|
| `accounts/urls.py`(9) | `sms/send`、`sms/verify`、`token/refresh` |
| `users/urls.py`(12) | `me`、`me/photos`、`me/photos/<int:photo_id>`、`me/preference`、`tags`、`<int:user_id>` |
| `im/urls.py`(7) | `user_sig` |
| `discovery/urls.py`(8) | `candidates`、`swipe` |
| `moderation/urls.py`(9) | `reports`、`blocks`、`blocks/<int:user_id>` |
| `feed/urls.py`(12) | `posts`、`posts/mine`、`posts/<int:post_id>`、`.../like`、`.../comments`、`.../report` |

> **注意 `<int:user_id>` 这类"路径参数"**：Django 会把这一段解析成 `int` 并作为关键字参数传给视图函数（P07 会看到 `def public_profile(request, user_id)`）。
> **注意 `users/urls.py` 里 `me` 必须排在 `<int:user_id>` 前面吗？** 不必——`me` 不是整数，`<int:...>` 匹配不上，所以不冲突。但 `feed/urls.py` 里 `posts/mine` 与 `posts/<int:post_id>` 同理安全。**这类"看起来危险其实安全"的地方，就是你要能自己论证的地方。**

## §4 动手实验

### 实验 1 · 亲手打一次"尾斜杠差异"

```powershell
# 另开终端先起服务器
cd D:\pycharmproject\chat_app\chatapp
python manage.py runserver 127.0.0.1:8000

# 再开一个终端
curl.exe -i http://127.0.0.1:8000/api/v1/health
curl.exe -i http://127.0.0.1:8000/api/v1/health/
```
**观察点**：第一条 200、第二条 404；两条都会在服务器终端留下带 `[request_id]` 的日志行。

### 实验 2 · 自己加一个接口（**唯一允许改 `config/api_urls.py` 的时刻，改完必须还原**）

在 `config/api_urls.py` 顶部加：

```python
from django.http import JsonResponse
```

在 `urlpatterns` 里加一行：

```python
path("ping", lambda request: JsonResponse({"pong": True})),
```

访问 `/api/v1/ping` → 200 `{"pong": true}`。然后：
1. 把它改成 `path("ping/", ...)`，再访问 `/api/v1/ping` 和 `/api/v1/ping/`，体会 APPEND_SLASH 的单向性（预期：`/api/v1/ping` → **301 重定向到 `/api/v1/ping/`**，`/api/v1/ping/` → 200）。
2. 把这一行和 `JsonResponse` 的 import **删掉**，跑 `git diff chatapp/config/api_urls.py` 确认干净。

### 实验 3 · 看清"路由顺序"到底会不会咬人

把 `path("", include("feed.urls"))` 挪到 `urlpatterns` 最前面，请求 `/api/v1/posts`，预期**仍是 401**（因为 moderation 的模式 `reports`/`blocks` 与 `posts` 无交集）。然后回答：**什么情况下这个挪动才会出事？**（答案思路：当两个模式能同时匹配同一路径时，先出现的那个永远赢。）改完还原。

## §5 自查题

**Q1. 请求 `/api/v1/users/me` 依次经过哪些 urls.py？**

**参考答案**：`config/urls.py`（第 10 行匹配前缀 `api/v1/`）→ `config/api_urls.py`（第 11 行匹配 `users/`，`include("users.urls")`）→ `users/urls.py`（第 6 行匹配 `me`）→ 调用 `users.views.me`。

**Q2. 为什么 `/api/v1/health/` 是 404，而不是 301 或 200？**

**参考答案**：本项目所有 `path()` 都不带尾斜杠（`config/api_urls.py` 第 8 行是 `path("health", health)`）。`CommonMiddleware` 的 `APPEND_SLASH` 只在"缺斜杠且补上能匹配"时重定向，反方向不处理，所以带斜杠的 URL 匹配不到任何模式 → 404。已实测。

**Q3. `asgi.py` 有没有生效？依据是什么？**

**参考答案**：没有。`config/settings.py` 第 92 行只设置了 `WSGI_APPLICATION`，全文没有 `ASGI_APPLICATION`；`config/asgi.py` 是 `startproject` 模板产物。部署用 gunicorn（WSGI）。聊天长连接由腾讯云 IM 承担，不需要 ASGI。

**Q4. 空前缀 include（`path("", include(...))`）为什么现在安全？**

**参考答案**：因为 moderation 与 feed 的模式（`reports`/`blocks`/`posts`…）与前面所有前缀（`auth/`、`users/`、`im/`、`discovery/`）以及后面两个具体路径（`matches`、`presence`）互不重叠。这是**当前事实**而非机制保证：新增接口若与既有模式重叠，先出现的 wins，必须自己检查。

**Q5. 导入 `config` 包时会顺带发生什么副作用？**

**参考答案**：`config/__init__.py` 第 3 行把 PyMySQL 注册成 `MySQLdb`（数据库驱动接管），第 5 行导入 Celery 应用对象（`celery_app`）。也就是说任何加载 `config.settings` 的进程都会初始化 Celery app——P10 会用到这个事实。
