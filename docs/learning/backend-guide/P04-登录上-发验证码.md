## §1 本批目标

1. 画出 `POST /api/v1/auth/sms/send` 的完整链路，指出**每一步失败会返回什么码**；

3. 解释验证码为什么在 Redis 里存的是摘要而不是明文；
4. 解释"入队失败必须回滚"这条业务决策。

## §2 读前必建概念

### 1）DRF 函数视图的装饰器栈（顺序有讲究）

```python
@api_view(["POST"])                      # 必须在最外层
@permission_classes([AllowAny])          # 覆盖全局权限（P02）
@throttle_classes([SmsSendThrottle])     # 覆盖/指定限流器
def sms_send(request): ...
```
装饰器**从下往上**依次包裹函数：先套限流、再套权限、最后 `api_view` 把普通函数变成 DRF 视图（负责解析请求、内容协商、异常收口）。**`@api_view` 必须写在最上面**，否则 DRF 的请求对象还没准备好。

### 2）`cache.add` 是原子的"占位"

`django.core.cache` 的 `add(key, value, timeout)` 语义：**仅当 key 不存在时写入并返回 True**，已存在返回 False。它对应 Redis 的 `SET key value NX EX ttl` 一条命令，所以并发安全。

对比"先 `get` 判断再 `set`"：两个并发请求可能都读到"不存在"，于是都发码——这就是为什么业务里凡是"只允许一次"的地方都用 `add` / `SETNX`。

### 3）Redis Lua 脚本 = 一段在 Redis 内原子执行的逻辑

验证码校验要做四件事：查锁 → 比对 → 错就计数（可能触发锁定） → 对就标记消费。**这四步之间不能插入别的请求**，否则并发爆破可以绕过"最多错 5 次"的限制。所以本项目把它们写成一段 Lua，交给 Redis 一次执行完。

### 4）存摘要，不存明文

`accounts/sms_codes.py` 第 60–61 行用 `SECRET_KEY` 做 HMAC-SHA256。**即使 Redis 被读走，也拿不到验证码明文**，更无法跨环境复用。（测试第 231 行 `test_code_is_not_stored_in_plaintext` 专门盯这条。）

### 5）入队失败的两种哲学：fail-open vs fail-closed

本项目选了 **fail-closed**：短信任务入不了队（用户根本收不到码）时，**回滚那个 60 秒占位**并返回 503。否则用户会陷入"没收到码，但 60 秒内不准重发"的死状态（`accounts/views.py` 第 73 行注释写明了这一点）。

| 8–15 | `PhoneSerializer`：字段声明 + `validate_phone` 单字段钩子（**`validate_<字段名>` 是 DRF 的命名约定**，会被自动调用） |
| 11–14 | 去空格 → 正则不匹配就 `raise serializers.ValidationError("手机号格式不正确")` |
| 18–19 | `SmsVerifySerializer(PhoneSerializer)` 继承复用手机号校验，只多一个"正好 6 位"的 `code` |

### 3. `accounts/views.py` 第 62–77 行 —— `sms_send`

| 行 | 在干什么 | 失败会怎样 |
|---|---|---|
| 62–64 | 三个装饰器：POST、公开、按 IP 限流 | 超 IP 额度 → 429（框架英文文案，见 `conventions.md` 第 117 行） |
| 66–68 | `is_valid(raise_exception=True)` → 拿到干净手机号 | 格式错 → 400 `{"code":400,...}`（经 P03 的异常处理器） |
| 69 | `services.issue_code(phone)` | 60 秒内重复 → `SmsSendTooFrequent` → **429 + code 42901 + `Retry-After: 60`** |
| 71 | `send_sms_code.delay(phone, code)` —— **Celery 入队**（真正的发送在 worker 里，P10） | 入队异常 → 第 74–76 行 |
| 74–76 | `rollback_send` 删占位与码 → 记 `logger.exception` → `raise SmsServiceUnavailable` | **503 + code 50301**（用户可立刻重试） |
| 77 | `Response({"status": "ok"})` | — |

> **注意第 71 行传的是 `code` 明文**：broker 里会有明文验证码（Redis DB1）。这是"内部队列"与"对外存储"的信任级差——P10 会看到任务体如何消费它。

### 4. `accounts/services.py`（41 行）

| 行 | 在干什么 |
|---|---|
| 13–14 | `_sent_key(phone)` → `sms:send:<phone>`（占位 key 命名） |
| 19–20 | `cache.add(_sent_key(phone), 1, settings.SMS_RESEND_INTERVAL)`；`add` 返回 False 说明 60 秒内已发过 → `SmsSendTooFrequent(wait=60)` |
| 21 | 开发模式用固定 `SMS_DEV_CODE`，否则 `f"{random.randint(0,999999):06d}"`（**注意 `:06d` 补前导零**） |
| 22–24 | `sms_codes.store(...)` 写 Redis → `logger.info` 打印验证码（开发期终端可见） |
| 27–30 | `rollback_send`：删占位 + 删码（fail-closed 的实现） |
| 33–41 | `check_code`：把 Lua 的返回码翻译成四种异常（见 P05） |

### 5. `accounts/sms_codes.py`（83 行）——**本批最硬的一段，建议逐行读两遍**

| 行 | 在干什么 |
|---|---|
| 14–36 | Lua 脚本。逐段读：17–19 锁存在 → 返回 4（LOCKED）；20–22 码不存在 → 返回 1（EXPIRED）；23–24 比对 `h` 字段；25–31 错则 `HINCRBY n 1`，达到上限就 `SET lock EX 900` + `DEL code` → 返回 3；32–35 对则 `HSET c 1` 并把 TTL 改成重放窗口 → 返回 0 |
| 38 | `_RESULTS = {0:"OK", 1:"EXPIRED", 2:"WRONG", 3:"JUST_LOCKED", 4:"LOCKED"}`——Lua 只能返回数字，这里做映射 |
| 40 | `CodeResult = Enum(...)`——**用枚举而不是裸数字**，调用方读起来才有意义 |
| 42–53 | `_get_script()` 惰性 `register_script` → 走 `EVALSHA`（脚本缓存，失败自动回退 `EVAL`）；`global _script` 是进程内缓存 |
| 56–57 | key 命名：`sms:code:<phone>`、`sms:lock:<phone>` |
| 60–61 | `digest(code)`：HMAC-SHA256(`SECRET_KEY`, code) |
| 64–68 | `store`：`HSET {h: digest, n: 0, c: 0}` + `EXPIRE 300`。**三个字段的含义**：h=摘要、n=错次、c=已消费标记 |
| 71–73 | `delete`（回滚用） |
| 76–83 | `verify`：把 4 个配置值作为 ARGV 传进脚本，返回 `CodeResult` |

### 6. `accounts/throttles.py`（20 行）

两个类结构相同：`scope` 指向 settings 第 220–221 行的额度名；`get_cache_key` 按 `self.get_ident(request)`（客户端 IP）拼 Redis 计数键。**`SimpleRateThrottle` 的计数也存在 Redis 里**，所以 P00 说的"Redis 停了限流也没了"就是这个类的行为。

### 7. `accounts/exceptions.py`（45 行）

| 类 | HTTP | detail_code | 备注 |
|---|---|---|---|
| `SingleDeviceSessionConflict` | 401 | 40101 | P05 用 |
| `SmsCodeExpired` | 400 | 40001 | — |
| `SmsCodeWrong` | 400 | 40002 | — |
| `SmsLocked` | 429 | 42902 | 第 32–34 行 `wait` 属性 → **本机实测带 `Retry-After: 900`** |
| `SmsSendTooFrequent` | 429 | 42901 | 继承 DRF `Throttled`，文案中文定制；实测 `Retry-After: 60` |
| `SmsServiceUnavailable` | 503 | 50301 | 入队失败 |

> **实测证据（2026-10-09）**：直接调用 `config.exceptions.api_exception_handler` 得
> `SmsLocked(wait=900)` → `{'code': 42902, ...}` + `Retry-After=900`；
> `SmsSendTooFrequent(wait=60)` → `{'code': 42901, 'message': '发送太频繁,请稍后再试 预计 60 秒后可用。'}` + `Retry-After=60`。
> 结论：DRF 的处理器对**任何**带 `wait` 属性的 `APIException` 都会加 `Retry-After`。

## §4 动手实验

### 实验 1 · 发一次码，然后去 Redis 里看它长什么样

```powershell
cd D:\pycharmproject\chat_app\chatapp
python manage.py runserver 127.0.0.1:8000     # 终端 A

# 终端 B
$body = @{ phone = "13800138000" } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/auth/sms/send `
  -ContentType 'application/json' -Body $body
```
预期：`status: ok`；**终端 A 的日志**里出现 `[开发模式] 验证码 phone=13800138000 code=123456`。

```powershell
docker exec chatapp-redis redis-cli HGETALL sms:code:13800138000
docker exec chatapp-redis redis-cli TTL sms:code:13800138000
docker exec chatapp-redis redis-cli GET sms:send:13800138000
docker exec chatapp-redis redis-cli TTL sms:send:13800138000
```
预期：hash 三个字段 `h`（64 位十六进制，**看不到 123456**）、`n=0`、`c=0`；第一个 TTL ≤300；`sms:send` 值 `1`，TTL ≤60。

### 实验 2 · 60 秒重发间隔（业务规则，不是框架限流）

紧接着再发一次同样的请求：
```powershell
try { Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/auth/sms/send -ContentType 'application/json' -Body $body }
catch { $_.Exception.Response.StatusCode.value__; $_.ErrorDetails.Message; $_.Exception.Response.Headers['Retry-After'] }
```
预期：**429** + `{"code":42901,"message":"发送太频繁,请稍后再试 预计 N 秒后可用。",...}` + `Retry-After` 为剩余秒数。

### 实验 3 · 连错 5 次触发锁定（本册读码状态机，P05 读登录）

```powershell
1..5 | ForEach-Object {
  $bad = @{ phone = "13800138000"; code = "000000" } | ConvertTo-Json
  try { Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/auth/sms/verify -ContentType 'application/json' -Body $bad }
  catch { "第 $_ 次: " + $_.Exception.Response.StatusCode.value__ + " " + $_.ErrorDetails.Message }
}
docker exec chatapp-redis redis-cli TTL sms:lock:13800138000
```
预期：第 1–4 次 `400` + `code 40002`；**第 5 次变成 `429` + `code 42902`**（Lua 返回 3 = JUST_LOCKED，说明"这一次也是最后一次"）；`sms:lock:*` 的 TTL ≈900；此后**即使传正确码也是 42902**。

## §5 自查题

**Q1. 为什么"60 秒只能发一次"用 `cache.add`，不用 `get` 后 `set`？**

**参考答案**：`add` 是一条原子命令（Redis `SET NX EX`），并发下只有一个请求能拿到 True；`get` + `set` 之间存在时间窗，两个并发请求可能都判定"没发过"，于是都发码，业务规则形同虚设。

**Q2. 验证码在 Redis 里存了什么？为什么？**

**参考答案**：`sms:code:<phone>` 是一个 hash：`h` = HMAC-SHA256(SECRET_KEY, code) 摘要、`n` = 错误次数、`c` = 是否已消费；TTL 默认 300 秒。存摘要使得 Redis 数据泄露也无法反推验证码（`sms_codes.digest` 第 60–61 行；测试第 231 行盯这一点）。

**Q3. 为什么校验要写成一段 Lua 而不是几条 Python 命令？**

**参考答案**：这四步（查锁／比对／计数／标记消费）必须整体原子。拆开执行时，并发的错误尝试可以穿插在"比对"和"计数"之间，绕过 `SMS_MAX_ATTEMPTS=5` 的上限；写成一个脚本后 Redis 单线程一次跑完（`sms_codes.py` 第 14–36 行）。

**Q4. 入队失败为什么要回滚？这是个什么取舍？**

**参考答案**：不回滚会留下死状态——用户没收到码，却被 60 秒占位挡着不能重发（`views.py` 第 73 行注释）。所以选 fail-closed：删掉占位与码，返回 503（50301），用户可立即重试。取舍点是"宁可让用户重试 + 看到明确错误，也不要让他卡住且无从下手"。

**Q5. 42901 与框架限流返回的 429 有什么不同？**

**参考答案**：42901 是业务规则（同号 60 秒重发间隔），`message` 是定制中文并带"预计 N 秒后可用"；框架限流（`SimpleRateThrottle` 超 IP 额度）的 `message` 是 DRF 英文默认文案、`code=429`。两者都带 `Retry-After`。见 `docs/api/conventions.md` 第 114–119 行。

**Q6. 开发模式下验证码是什么？为什么日志里能直接看到？**

**参考答案**：固定 `123456`（`SMS_DEV_MODE=1` → settings 第 239–240 行），并且 `services.issue_code` 第 23 行主动 `logger.info` 打印。目的是本地/联调不依赖短信商。
