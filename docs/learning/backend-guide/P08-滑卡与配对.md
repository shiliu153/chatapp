## §2 读前必建概念

### 1）`UniqueConstraint` 是最后一道防线

```python
constraints = [models.UniqueConstraint(fields=["swiper", "target"], name="uniq_swipe_swiper_target")]
```
应用层的 `get_or_create` 能处理绝大多数重复请求，但**并发下仍可能两个请求同时判定"不存在"**。数据库的唯一约束是最终保证：重复插入会抛 `IntegrityError`。**应用层负责体验，数据库层负责正确性。**

### 2）`CheckConstraint` 保证"同一对只有一行"

`Match` 表用两个用户外键表示一对关系。若不规定顺序，`(1,2)` 与 `(2,1)` 会是两行，配对列表就会重复。项目用：
- `CheckConstraint(condition=Q(user_a__lt=F("user_b")))` —— 强制 `user_a.id < user_b.id`
- `UniqueConstraint(fields=["user_a", "user_b"])` —— 这一对只允许一行
- `Match.pair_kwargs(user1, user2)` 类方法 —— 写入前**统一按 id 排序**，让 "A 喜欢 B" 与 "B 喜欢 A" 落到同一行

### 3）`get_or_create` 的返回值

`obj, created = Model.objects.get_or_create(**条件, defaults={...})`：`created=True` 表示这次真的插入了。**"只在第一次插入时做副作用"** 是幂等接口的标准写法（本项目用它决定要不要发配对灰条）。

### 4）`transaction.atomic()` 与 `on_commit` 的关系

`atomic()` 把一段操作包成一个事务；`on_commit` 注册的回调**只在事务成功提交后执行**。本项目在 `atomic()` 内部创建 `Match`，再由 `services.notify_match` 用 `on_commit` 排队发灰条——保证"库里有配对，才可能发通知"。

### 5）`order_by("?")` 是随机排序

`ORDER BY RANDOM()`（MySQL 上是 `RAND()`）：每次请求给出不同的候选顺序。代码第 59 行注释自己承认"数据量大时会慢，MVP 阶段几百人够用，将来换成预计算随机列"——**读到这种注释要记下来，这是演进路标**。

### 6）什么时候需要手工调用分页器

DRF 的自动分页只对"返回 queryset 的通用视图"生效。本项目全是 `@api_view` 函数视图，所以要自己 `paginate_queryset` + `get_paginated_response`（`match_list` 第 106–108 行就是这么干的）。

## §5 自查题

**Q1. 候选卡排除了哪五类人？**

**参考答案**：①自己 ②我已划过的人 ③我已配对的人 ④被我/我拉黑的人（`blocked_user_ids`）⑤资料未完善（`status != complete`）或没有已过审照片的人。此外还会按偏好过滤性别/城市/年龄区间。

**Q2. `birthday_bounds` 在这里怎么用的？为什么用 `lte` + `gt`？**

**参考答案**：第 51–52 行把年龄区间换算成生日区间：`birthday__lte=upper, birthday__gt=lower`。上界是"今天减 age_min 年"（生日不晚于它 → 年龄 ≥ age_min），下界是"今天减 (age_max+1) 年"（生日晚于它 → 年龄 ≤ age_max）。左开右闭是为了让边界人群不重不漏，与 `birthday_bounds` 第 22–23 行的推导一致。

**Q3. `Swipe` 的 `UniqueConstraint` 与 `get_or_create` 是不是重复劳动？**

**参考答案**：不是。`get_or_create` 是应用层优化（避免异常、保留首次动作），但并发下两个请求可能同时判定"不存在"并都尝试插入；`UniqueConstraint` 是数据库层的最终保证，会拦下第二条。**应用层管体验，数据库层管正确性。**

**Q4. `Match` 为什么要有 `CheckConstraint(user_a < user_b)`？**

**参考答案**：确保同一对用户在表里只有一种表示（否则 `(1,8)` 与 `(8,1)` 会成为两行，配对列表重复、唯一约束也形同虚设）。`pair_kwargs` 负责写入时排序，`CheckConstraint` 负责"哪天有人绕过 `pair_kwargs` 直接写"时立刻报错。

**Q5. `swipe` 的"幂等"体现在哪两处？重复提交会重复发灰条吗？**

**参考答案**：第一层 `Swipe.get_or_create`（重复提交保留首次动作与结果）；第二层 `Match.get_or_create` + 只有 `created` 才 `notify_match`（第 89–91 行）。所以重复提交不会重复发灰条，但返回值仍是 `matched: true`（因为"双方都 like 过"这个事实为真）。

**Q6. `match_list` 为什么要手工调用分页器？**

**参考答案**：DRF 自动分页只作用于返回 queryset 的通用视图；本项目是函数视图，且 `match_list` 先把 queryset 转成了 list of dict（`_match_entry` 需要 request 拼绝对 URL），所以必须自己 `paginate_queryset` + `get_paginated_response`。第 106 行注释还提醒：靠 `Match.Meta.ordering` 保证翻页顺序稳定。

**Q7. `order_by("?")` 有什么代价？作者留下什么演进方向？**

**参考答案**：数据库要对全表做随机排序（MySQL `RAND()`），数据量大时很慢。第 59 行注释给出方向：将来换成"预计算随机列"。**这类注释是项目的技术债地图，值得抄进笔记。**

**Q8. 为什么滑卡限流按用户、发短信限流按 IP？**

**参考答案**：维度取决于"攻击者最容易换什么"。滑卡额度是业务公平性（按人算），换 IP 不该绕过 → 按 `user.id`；发短信是防刷成本（按来源算），换手机号不该绕过 → 按 IP（`throttles.py` 两处的 `get_cache_key` 就是全部差别）。
