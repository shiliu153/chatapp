# 广场页(动态流)设计

日期:2026-09-12
状态:已与用户逐节确认(见 §8 决策记录),待用户终审
上游:M3 合规(`specs/2026-09-11-m3-compliance-design.md`)、微信式改版(`specs/2026-09-12-chat-profile-wechat-design.md`)
背景:用户提出新页面需求 —— 「广场」页,大家可发布动态(文字 + 图片),信息流布局类似微博,配互动(点赞/评论)与运营管理。

## 1. 目标与范围

1. 底部导航新增第 4 个 tab「广场」(顺序:发现 / 广场 / 消息 / 我的),微博式信息流。
2. 发布动态:文字(≤500 字)+ 图片(≤9 张,单张 ≤5MB),两者至少其一。
3. 互动:点赞(一人一赞,可取消)+ 评论(一级,时间正序)。
4. 内容安全:文字走现有敏感词库同步拒(400);图片直接展示,不前置审核。
5. 运营台 /ops/ 新增「动态管理」页:浏览全部动态 + 删除违规动态。
6. 可见性沿用全应用「拉黑 = 双向不可见」语义。
7. 评论以「系统通知」身份通知动态作者(点赞不通知)。
8. **动态举报**:可举报他人动态,进入运营台「动态举报」队列;运营审核后「删除动态」或「忽略」;处理完成给举报者发系统通知(复用 `report_handled`)。

**非目标(YAGNI):** 转发、关注/粉丝、话题/@、二级评论与评论点赞、删自己的评论、热门/推荐算法(只按时间倒序)、动态删除审计留痕、新动态未读红点、举报后自动隐藏(采用先举报后审核、期间可见)。

## 2. 数据模型(新 app `feed`,五张表)

| 模型 | 字段 | 约束 |
|---|---|---|
| `Post` | author(FK User)、text(TextField, ≤500, 可空)、created_at | 文字与图片至少其一(序列化器校验) |
| `PostImage` | post(FK, related_name="images")、file(ImageField, `posts/%Y/%m/`)、order | 最多 9 张、单张 ≤5MB(序列化器校验) |
| `PostLike` | post(FK, related_name="likes")、user(FK)、created_at | 唯一约束 (post, user) |
| `PostComment` | post(FK, related_name="comments")、author(FK)、text(≤200)、created_at | — |
| `PostReport` | reporter(FK User, related_name="post_reports")、post(FK, related_name="reports")、type(复用 `moderation.ReportType`)、detail(≤200, 可空)、status(复用 `moderation.ReportStatus`, 默认 pending)、handled_note、handled_by(可空)、handled_at(可空)、created_at | 同人同动态仅一条 pending(接口层保证,与举报用户一致) |

沿用项目「一张图一行」模式(与 `users.Photo` 一致)。删除动态时显式删除图片文件(ImageField 删行不会自动删文件)。

## 3. 接口设计(前缀 `/api/v1`,均挂现有鉴权 + 重封禁全域 403 自动覆盖)

| 接口 | 说明 |
|---|---|
| `GET /posts` | 广场流,最新在前,limit/offset 分页(复用 `config/pagination.py`) |
| `POST /posts` | multipart 发布:字段 `text`(可空)+ `images`(重复字段,0-9 个);成功 201 返回动态对象;限流 20/天 |
| `GET /posts/{id}` | 动态详情(响应结构同流内单条) |
| `DELETE /posts/{id}` | 删除动态:仅作者本人;连带图片文件、点赞、评论 |
| `POST /posts/{id}/like` | 点赞(已赞则幂等返回 200) |
| `DELETE /posts/{id}/like` | 取消赞(未赞幂等 204) |
| `GET /posts/{id}/comments` | 评论列表,时间正序,分页 |
| `POST /posts/{id}/comments` | 发评论 `{text}`;敏感词同检;限流 60/天 |
| `POST /posts/{id}/report` | 举报动态 `{type, detail?}`(type 复用 `moderation.ReportType` 四类);成功 201;同人同动态已有待处理 → 幂等 200 返回已有;限流 20/天 |
| `GET /posts/mine` | 我的动态(仅自己的,最新在前,分页) |

**单条动态响应字段:**

```json
{
  "id": 1,
  "author": {"user_id": 8, "nickname": "Alice", "avatar_url": "http://..."},
  "text": "今天天气真好",
  "images": ["http://.../media/posts/2026/09/x.jpg"],
  "like_count": 3,
  "comment_count": 1,
  "liked_by_me": false,
  "created_at": "2026-09-12T20:00:00+08:00"
}
```

**单条评论响应字段:**

```json
{
  "id": 5,
  "author": {"user_id": 9, "nickname": "Bob", "avatar_url": "http://..."},
  "text": "好漂亮",
  "created_at": "2026-09-12T20:05:00+08:00"
}
```

`avatar_url` 取第一张已过审资料照片(与 `/matches`、拉黑列表同源逻辑)。计数实时 `annotate` 查询,不存冗余计数字段。

## 4. 业务规则

**流的过滤(三条):**
1. 双向拉黑关系过滤(复用 `moderation.services.blocked_user_ids`)。
2. 重封禁(`banned_heavy`)作者的历史动态**隐藏**(封号 = 内容下架);轻封禁(`banned_light`)照常展示与发布。
3. 敏感词仅作用于写入(发布/评论),不回溯过滤存量。

**不可见规则的适用范围(与拉黑资料页 404 同模式):**
- 作用于:广场流、动态详情、评论列表、点赞/评论/举报的写入。
- 详情/点赞/评论一个不可见(双向拉黑关系、或作者重封禁)的动态 → 一律 **404**;评论列表同时不出现「与我双向拉黑的人」及「重封禁者」的评论。
- `GET /posts/mine` 是看自己,不受上述过滤。

**校验(序列化器层,违反即 400 中文报错):**
- 文字与图片至少其一;文字 ≤500;评论 ≤200;图片 ≤9 张;单张 ≤5MB。
- 文字(发布与评论)命中 `find_blocked_word` → 400(与昵称/简介同一套词库、同一种处理)。
- 限流:发布 20/天、评论 60/天(DRF throttling,计数在 Redis,429 带 `Retry-After`)。

**动态举报规则:**
- 举报自己的动态 → 400(纵深防御,UI 不提供入口);不可见动态(双向拉黑 / 作者重封禁)→ 404(与点赞评论同一可见性校验);type 必须在四类内 → 否则 400。
- **先举报后审核,期间动态照常可见**;同人同动态已有 pending → 幂等返回已有记录(200),不新建。
- 运营处理(ops):「删除动态」复用动态删除服务(删动态 + 图片文件 + 评论点赞),同时该动态**全部 pending 举报**一并标记 handled(handled_note「动态已删除」);「忽略」只标记该条 handled(可填备注)。两个动作都对相关举报者入队 `report_handled` 通知(复用 `moderation.services.notify_report_handled`,传 `PostReport` 同样成立——只取 `reporter_id`);**只在 pending → handled 迁移点入队**,重复处理不重发。

**评论通知(全链):**
- `im/client.py::send_post_commented(to_identifier, commenter_nickname, snippet) -> bool` — 以 `system_notice` 身份发 custom `{"type": "post_commented"}`,Desc = 「{昵称} 评论了你的动态:{摘要}」(摘要截断 50 字)。
- `im/tasks.py::post_commented(comment_id: int)` — 任务参数一律 user_id 的既定约定在此用 comment_id(文案需要评论者与内容);任务内查库,评论/作者/评论者任一缺失静默返回;**评论者是作者本人时不发**(自己评自己不打扰)。
- `feed/services.py::notify_post_commented(comment)` — `_enqueue(im_tasks.post_commented, comment.id)`,在评论创建后调用(on_commit + robust)。
- App 端在 `ChatMessageKind.banNotice` 白名单加 `post_commented`(与 `report_handled` 同款一行映射,灰条渲染)。

## 5. 前端设计(新 `features/square/`)

**底部 tab(改 `home_shell.dart`)**:4 项,顺序 发现 / 广场 / 消息 / 我的;广场图标九宫格(`Icons.grid_view_outlined` 语义贴图片流);消息红点逻辑不动。

**广场页 `square_page.dart`**:信息流卡片列表(下拉刷新 + 滚到底自动加载下一页),右下角悬浮「+」。
- 卡片(`widgets/post_card.dart`):头像 + 昵称 + 相对时间(新工具函数:`x 分钟前 / x 小时前 / x 天前 / 日期`)+ 正文 + 九宫格图 + 底部 点赞/评论 计数行。
- 交互:点头像/昵称 → 现有用户资料页 `/users/:id`;点卡片其余区域 → 详情页;点图片 → 全屏预览(黑底、左右切换、可缩放);点赞乐观更新(先变红后请求,失败回滚 + SnackBar)。
- 卡片右上角「···」菜单:**自己的动态** → 「删除」(确认框);**别人的动态** → 「举报」→ 复用现有 `ReportSheet`(四类原因 + 补充说明)→ `POST /posts/{id}/report` → SnackBar「已收到举报,我们会尽快处理」。
- 空态:「还没有动态,发一条吧」+ 刷新按钮。

**发布页 `post_compose_page.dart`**(全屏 push 路由 `/posts/compose`):多行文字框(500 字计数)+ 九宫格选图(点格子追加,最多 9 张,复用资料照片的 image_picker + `MultipartFile.fromBytes` 方案)+ AppBar 右上角「发布」;空内容(无文字无图)置灰;发布中禁止重复提交;成功 pop 回广场并 `invalidate` 流。

**详情页 `post_detail_page.dart`**(路由 `/posts/:id`):顶部完整动态卡片(点赞可操作;右上角同款「···」菜单:作者 = 删除、非作者 = 举报)+ 评论列表(时间正序,分页加载)+ 底部固定输入框(发送中禁用,成功清空并追加到列表末尾)。

**我的动态页 `my_posts_page.dart`**(路由 `/my-posts`):「我的」页新增一行入口「我的动态」;列表复用 `post_card`(可删),分页加载。

**状态层**:`square_repository.dart`(纯 IO,JSON → 模型);流/详情/我的各自 provider(带 `autoDispose`,防订阅泄漏);发布/点赞/评论/删除成功后 `invalidate` 对应列表。

**九宫格排版**:1 张大图;2-4 张两列;5-9 张三列(微博规则)。`widgets/photo_grid.dart` 独立组件,广场/详情/我的三处复用。

## 6. 运营台 /ops/(动态管理 + 动态举报)

**动态管理**(`/ops/posts/`,菜单新增项):
- 列表最新在前,每行:第 1 张图缩略图 + 作者(昵称 + 手机号)+ 文字摘要 + 赞/评数 + 创建时间 + 行尾「删除」按钮;HTMX 局部刷新(与现有页面同款模式)。
- 删除 = 删动态 + 图片文件 + 连带评论点赞(与作者删除同一服务函数)。
- **不做审计留痕**(本期);版权/纠纷场景以后统一做运营操作日志。

**动态举报队列**(`/ops/post-reports/`,菜单新增项,与现有「举报队列」同款):
- 状态筛选(pending 默认)+ 类型筛选;列表行:动态摘要(文字截断 + 第 1 张缩略图)+ 作者(链接到用户详情,封禁走已有链路)+ 举报人 + 原因 + 状态 + 时间。
- 行内动作:**「删除动态」**(复用动态删除服务;该动态全部 pending 举报一并标记 handled「动态已删除」;给各举报者入队通知)/ **「忽略」**(该条标记 handled,可填备注,同样通知)。HTMX 局部刷新。
- 重复处理幂等:已删除的动态 / 已处理的举报,再点只重渲染面板。

## 7. 测试与验证

**后端(预计 +27~32 个用例,全量 256 保持全绿):**
- 发布:纯文字/带图成功;空内容、超 9 张、超 5MB、敏感词 → 400;未登录 401;重封禁 403;限流 429(缩小 rate 用 patch)。
- 流:最新在前、分页、双向拉黑过滤、重封禁作者隐藏、`liked_by_me`/计数正确。
- 点赞:创建、重复幂等、取消幂等、计数。
- 评论:成功、敏感词 400、正序、通知入队(patch `im.tasks.post_commented.delay` + `captureOnCommitCallbacks`)、自己评自己不通知。
- 删除:作者可删(断言行与文件均删)、非作者 404、运营可删。
- 举报:新建 201、同人重复幂等 200、举报自己 400、不可见动态 404、无效 type 400、限流 429(patch rate)。
- mine:只含自己的。
- 任务体:mock `im.client.*`,断言收件人与文案、评论缺失静默(腾讯 REST 一次不真打)。
- ops:`/ops/posts/` 权限、列表、删除;**`/ops/post-reports/`** 权限、筛选、忽略(标记 + 通知入队)、删除动态(动态消失 + 全部 pending 标记 + 各举报者通知入队 + 文件删除)、重复处理不重发。

**Flutter(预计 +12~15 个用例,全量 157 保持全绿,analyze 零告警):**
- tab 4 项与广场可切换;卡片渲染(昵称/文字/时间/计数);空态;点赞乐观更新与失败回滚;发布页空内容置灰与 9 张上限;详情页评论渲染与发送;我的动态删除;`post_commented` → 灰条映射;「···」菜单(自己 = 删除、别人 = 举报)与举报提交。

**手测(双模拟器 + /ops/):**
1. A 发文字 + 多图动态 → B 广场可见;B 点赞、评论 → A 消息页「系统通知」收到评论灰条;点赞不产生通知。
2. 图片点开全屏、左右切换、缩放。
3. A 删自己的动态 → 双端列表消失;B 尝试访问详情 404。
4. 双向拉黑后互相看不到动态;重封禁用户动态隐藏、轻封禁照常。
5. ops 动态管理页可见全部动态并删除,B 端刷新后消失。
6. 敏感词发动态/评论被 400 拒;发布限流触发 429。
7. B 举报 A 的动态 → ops「动态举报」队列可见 → 「删除动态」→ 双端消失,B 收到「举报已处理」系统通知;另一条用「忽略」路径,B 也收到通知、动态保留。

## 8. 关键决策记录

- 入口:底部加第 4 个 tab,置于「发现」与「消息」之间(用户选 1)。
- 动态形态:文字 + 图片 ≤9 张九宫格,至少其一(用户选 1)。
- 互动:点赞 + 评论,不做转发(用户选 1)——交友场景转发无落点(个人主页无动态流)。
- 审核:文字敏感词同步拒 + 图片直接展示(用户选 1,与昵称/简介同模式);ops 补「动态管理」页(用户要求)。
- 可见性:过滤双向拉黑关系(用户选 1),保持全应用语义一致。
- 通知:评论发系统通知、点赞不发(用户选 1);文案带摘要,自己评自己不打扰。
- 自己的动态:广场可删 + 「我的」页加「我的动态」入口(用户选 2)。
- 评论形态:点动态进详情页(用户选 1,微博同款)。
- 发布入口:右下角悬浮「+」→ 全屏发布页(用户选 1)。
- 发布实现:一步 multipart(方案 A,用户选 A)——实现与排查最简;两步(先传图)留待体验需要时演进。
- 动态举报(用户补充):先举报后审核、期间动态照常可见(选 1,防恶意举报下架);独立「动态举报」队列页(选 1);处理动作 = 删除动态 / 忽略 + 作者链接(选 1,封禁复用已有用户链路);处理完成给举报者发系统通知(复用 `report_handled` 机制)。
- 视觉沟通:用户明确不开浏览器伴生页,版式按本文文字描述实现。
