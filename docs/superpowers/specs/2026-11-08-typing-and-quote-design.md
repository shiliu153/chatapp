# 输入中状态 + 引用回复设计

- **日期**:2026-11-08
- **状态**:待实施(批次 L,第六轮功能开发第二批)
- **上游**:第六轮功能开发拆批(K → **L** → M → N → O);批次 K 已合并(`37eaf56`),多端在线已就绪

## 1. 目标与非目标

**目标**:① 对方正在打字时,聊天页顶栏显示「对方正在输入…」;② 长按消息可以「引用」,气泡上方显示被引用内容,点击可跳回原消息。

**非目标**(本批不做):
- 会话列表行的 typing 提示(已拍板只做聊天页顶栏)
- 引用跨会话 / 引用系统灰条
- 引用的「取消引用」以外的编辑能力(引用条只可关闭)
- typing 的离线补拉(纯瞬时状态,不落库)
- 已读回执、撤回语义的任何改动

## 2. 已拍板的决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 引用内容怎么存 | **`ref_msg_id` + 服务端生成的快照** | 历史分页意味着被引用消息常常不在客户端内存里,只存 id 会大量显示「原消息不可见」 |
| 快照由谁生成 | **只能服务端** | 客户端传快照 = 任何人可伪造「对方说过 X」;与批次 J 贴纸「只落白名单字段」同一原则 |
| typing 展示位置 | **只聊天页顶栏** | 最小、最常见、不打扰;列表行实时刷新收益不足 |
| typing 是否落库 | **否** | 纯瞬时状态;落库既无意义又给写入路径加压 |

## 3. L-1 输入中状态

### 3.1 协议

**上行**(客户端 → 服务端),无 `id`、**不 ack**:

```json
{"v":1,"type":"typing","data":{"to":"u14"}}
```

**下行**(服务端 → **对端**),与 K-2 的扇出一致(对端若多端在线,两端都收):

```json
{"v":1,"type":"typing","data":{"peer":"u12"}}
```

语义:`peer` 是**收帧者**的对端(即正在打字的人)。

### 3.2 服务端行为

| 项 | 规则 |
|---|---|
| 落库 | **不落** |
| 前置校验 | `im_pair` 必须存在(与 `send` 同口径);目标不存在 / 未配对 / 被拉黑 → **静默丢弃**(不回错误帧) |
| 限流 | 每连接 **1 次 / 2 秒**令牌桶(突发 3);超限**静默丢弃** —— 不回 `42901`,避免给洪泛者反馈 |
| 扇出 | 只发对端(`registry_.send_to(peer_uid, ...)`),**不发给自己其他端** |
| 离线 | 对端不在线 → 什么都不做(不排队、不补拉) |

**为什么不回错误**:typing 是「可丢」信号,回错误只会让客户端在限流时弹提示,而用户看到的应是「对方没在打字」而已。

### 3.3 客户端行为

| 端 | 发送 | 接收 |
|---|---|---|
| 共同 | 首次输入**立即发**,之后**每 3 秒最多一次**;输入框清空 / 发送后**不再发** | 收到即显示,**5 秒内没有新帧自动隐藏**;离开会话页立即清掉 |
| App | 输入框 `onChanged` 触发节流发送 | 聊天页顶栏(昵称下方)显示「对方正在输入…」 |
| Web | 同上 | 同上 |

> 节流放在**客户端**(3 秒)与**服务端**(2 秒)两层:客户端省流量,服务端防伪造。

## 4. L-2 引用回复

### 4.1 协议

`send` 帧的 `data` 增加**可选**整数 `ref_msg_id`:

```json
{"v":1,"type":"send","id":"m1","data":{"to":"u14","kind":"text","text":"好,六点","ref_msg_id":123}}
```

下行 `message` 帧与 `/im/api/messages` 的每一项增加**可选** `ref` 对象(没有引用时不出现该键,老客户端不解析也不会崩):

```json
"ref":{"msg_id":123,"from":"u12","kind":"text","text":"今晚吃饭?","revoked":false}
```

### 4.2 服务端行为

1. **校验**:`ref_msg_id` 必须存在于**同一 conv**,否则 `42201`(与其它参数错误同码,不新增业务码);
2. **生成快照**(客户端传来的任何 `ref` 内容一律忽略):取被引用消息的 `from_id` / `kind` / 摘要:
   - `text` → 前 120 字
   - `image` → `[图片]`、`voice` → `[语音]`、`custom/sticker` → `[贴纸]`
   - 已撤回 → `text` 留空 + `revoked: true`
3. **落库**:`im_message` 新增两列(`ref_msg_id` / `ref_snapshot`),随消息一次插入;
4. **不可引用**:系统灰条(`kind=2` 且 `type` 为 `match_notice` / `ban_notice` 等非 sticker 载荷)一律 `42201`。

### 4.3 存储

迁移 `imserver/migrations/006_quote.sql`(**只加可空列**,在线安全):

```sql
ALTER TABLE im_message
  ADD COLUMN ref_msg_id BIGINT UNSIGNED NULL,
  ADD COLUMN ref_snapshot TEXT NULL;
```

快照是 JSON 文本(字段同 §4.1 的 `ref`),读时原样透出,不再二次查库 —— 这正是「快照」的意义。

### 4.4 客户端

| 端 | 交互 |
|---|---|
| 共同 | 长按/右键消息 → 菜单多一项「引用」→ 输入栏上方出现引用条(可关闭)→ 发送时带 `ref_msg_id` |
| 显示 | 气泡上方渲染引用块(发送者昵称 + 摘要);`revoked: true` 显示「消息已撤回」;点击引用块跳到原消息(本地已加载则滚动定位,未加载则提示「原消息不在当前记录中」) |
| 边界 | 引用自己发的消息允许;引用**灰条**入口不出现(灰条本来就不能长按出菜单) |

## 7. 风险

| 风险 | 处置 |
|---|---|
| typing 被拿来做洪泛 / 探测在线 | 服务端令牌桶 + `im_pair` 前置 + 静默丢弃;不落库,不产生写放大 |
| 客户端伪造引用内容 | **快照只由服务端生成**,客户端只传 id |
| 老客户端解析新字段崩 | `ref` 键**只在有引用时出现**;typing 是新 `type`,老客户端按未知帧忽略(既有行为) |
| 迁移风险 | 只加可空列,不改既有列;回滚 = 回退镜像(列留着不影响旧代码) |
