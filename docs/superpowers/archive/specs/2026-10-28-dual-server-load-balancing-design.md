# 双机负载均衡架构方案 v2（跨云约束下修订）

- 日期：2026-10-28（v2 修订；v1 假设「同云内网互通」，已被现实推翻）
- 状态：架构设计，**不含实施计划、未改代码**
- 新约束：第二台是 **AWS**，与阿里云**不同云、无内网**；DNS TTL **只能 600 秒**；接受 5–15 分钟人工接管；不加入口机；B 有公网 IP。

---

## 0. 结论先行（三句话）

1. **跨云的「第二台」不能当 Django 应用副本**。Django 每个请求要串行访问 MySQL/Redis 若干次，跨公网 RTT 会直接乘到每个请求上；媒体和 IM 会话表也没法跨云共享。这不是配置问题，是物理问题。
2. **所以「两台一起做负载均衡」在跨云前提下不成立**。能成立的只有两条：第二台放到**阿里云同地域**（真双机），或者**不双机、只升配**，把 AWS 用在它擅长的地方（海外边缘缓存 / 异地备份 / 监控）。
3. 若 AWS 是**海外区**，还有一条比延迟更硬的红线：**手机号、聊天记录、照片出境**属于个人信息出境，交友类应用尤其敏感，合规成本远高于机器钱。

## 1. 新约束清单（以及它们各自杀死了什么）

| 约束 | 直接后果 | 被杀死的设计 |
|---|---|---|
| 跨云、无内网 | 所有跨机流量走公网 + TLS，RTT 40–250ms（看 region） | MySQL 主从、Redis 主从、NFS 共享、IM 跨节点投递 |
| DNS TTL 600 秒 | 故障切换最坏 10 分钟才全量生效 | 「秒级切换」；无健康检查的 DNS 轮询 |
| 无入口机 / 不买 SLB | 入口就是某一台机器 | 入口冗余 |
| 接受 5–15 分钟接管 | 可以走「人工提升 + DNS 切换」 | 需要自动选主的设计 |
| B 有公网 IP | 可以直连、可以当备用入口 | — |

## 2. 为什么跨云双活不成立（三条硬理由）

### 2.1 数据层跨不过去：延迟会被「请求内的查询次数」放大

这是最容易被低估的一点。假设一次 `GET /discovery/candidates` 平均 8 条 SQL（列表 + 照片 + 标签 + 计数，属正常量级；可用 `connection.queries` 实测校准）：

| 场景 | 单条 SQL 往返 | 一个请求的 DB 时间 | 结论 |
|---|---|---|---|
| 同机（今天） | ~0.1ms | ~1ms | 基线 |
| 同 VPC 跨机 | ~0.3ms | ~2.4ms | 可用 |
| 跨云同城/近邻（香港、新加坡，RTT ~40ms） | 40ms | **~320ms** | 比今天慢一个数量级 |
| 跨云远距离（东京 ~60ms / 弗吉尼亚 ~220ms） | 60–220ms | **~0.5–1.8s** | 不可用 |

**注意**：`CONN_MAX_AGE` 只省掉建连握手，省不掉每条查询的往返。Django 的 ORM 是同步串行的，没有批量流水线。

所以把 Django 放在 AWS、数据库留在阿里云，**不是「加了一台机器分担流量」，而是「让每个请求多花几百毫秒」**——吞吐会掉，不是涨。

反向也一样：把 MySQL 搬到 AWS，阿里云那台就变成慢的。

### 2.2 媒体文件跨不了云

今天的照片/聊天图/语音都在 `MEDIA_ROOT` 本机盘（`chatapp/config/settings.py:404`）。

- NFS over 公网：不可行（延迟、丢包、安全、跨境）。
- rsync 双向同步：有窗口期 → 「随机一半图片 404」，且冲突无解。
- 唯一正确的跨云做法是**对象存储 + CDN**（OSS/S3），但这就回到「要买新服务」，而且涉及数据出境。

### 2.3 IM 双活跨不了云

v1 设计里「Redis 记 owner + 内部 HTTP 转发」的前提是**内网毫秒级**。跨云后：

- 每条跨节点消息多 40–250ms，聊天体验直接崩；
- 会话表仍在进程内（`imserver/src/service/session_registry.h:26`），WS 长连接跨境抖动会导致大面积重连；
- DNS 600 秒意味着「节点挂了，一半用户 10 分钟内连的是死 IP」。

### 2.4 合规红线（如果 AWS 是海外区）

手机号、聊天内容、照片、城市 → **个人信息**；交友资料里的性别/取向偏好还可能构成**敏感个人信息**。把这些放到境外服务器，按《个人信息保护法》需要单独同意 + 个人信息出境标准合同/安全评估/认证之一。这是法务动作，不是技术动作，周期以周计。

> 如果 AWS 是**中国区**（北京/宁夏），这一条不成立，但 §2.1–2.3 依然成立。

## 3. 三条可行路线

| | **R1 同云双机（推荐）** | **R2 只升配（最省事）** | **R3 AWS 跑 Django（不推荐）** |
|---|---|---|---|
| 形态 | 再买一台**阿里云同地域**，与现有 A 组成 v1 的双机 | 保持单机，把 A 升到 4C8G | AWS 跑应用，跨云隧道连 A 的 DB |
| AWS 的角色 | 海外边缘缓存 + 异地备份 + 外部探针 | 同左 | 应用节点 |
| 容量 | ~2× | ~2–3×（CPU 核数翻倍） | **反而下降**（§2.1） |
| HA | B 挂无感；A 挂 5–15 分钟接管 | 无（单点） | 无（跨云依赖更脆） |
| 额外成本 | 1 台 2C2G（约 ¥60–100/月） | 升配差价（约 ¥100–200/月） | 0（但 AWS 流量费 + 合规成本） |
| 改造量 | 中（IM 双活代码） | **极小**（只改配置/规格） | 大（多库路由 + 隧道 + 一致性） |
| 风险 | 中 | 低 | 高 |

**推荐顺序：R2 → R1**。

理由很直接：你现在的瓶颈是 **CPU 核数**（`README.md` 容量一节的原话是「瓶颈已经从 worker 数转为 CPU 核数」），而跨云加机器解决不了 CPU 问题。**先把 A 升配**，是最便宜、当天生效、零架构风险的一步；如果升配后还不够，再买同云第二台做真双机。

AWS 那台不浪费：它有公网 IP、在境外，天然适合做**海外静态/图片边缘 + 异地备份 + 外部可用性探针**（详见 §5）。

## 4. R1 详细架构（同云双机）

> 这一节是 v1 §4–§6 的延续，前提改成「两台都在阿里云同地域、内网互通」。跨云版本没有对应设计，因为不存在。

```
DNS(600s): chat.shiliu153.cn → A 公网 IP
                     │
        ┌────────────▼─────────────┐        内网互通（同地域）
        │ A  10.0.0.1              │◄──────────────┐
        │ nginx 443 入口            │               │
        │ gunicorn 127.0.0.1:8000  │               │
        │ celery worker            │               │
        │ imserver 127.0.0.1:9100  │               │
        │ MySQL 主 + Redis 主       │               │
        │ NFS server（媒体）        │               │
        │ 定时任务（清理/备份/探针） │               │
        └────────────┬─────────────┘               │
                     │                             │
        ┌────────────▼─────────────┐               │
        │ B  10.0.0.2              │───────────────┘
        │ nginx 443 备用入口        │
        │ gunicorn 127.0.0.1:8000  │
        │ celery worker            │
        │ imserver 127.0.0.1:9100  │
        │ MySQL 从 + Redis 从       │
        │ NFS client（同路径挂载）  │
        └──────────────────────────┘
```

关键点（细节见 v1 文档 §5–§6，仍然有效）：

- `/api/v1/` → `upstream{A:8000, B:8000}`，`least_conn` + keepalive。
- `/media/` → NFS 挂载点直出（路径两台完全一致）。
- `/im/ws?node=a|b` → `map $arg_node`，**不要用 `ip_hash`**（移动端 CGNAT 会把整个运营商出口压到一台）。
- IM 双活 = Redis 记 owner + 内部 HTTP `/internal/deliver`（仅内网成立）。
- `NUM_PROXIES` 与实际代理跳数必须一致；`IM_TRUSTED_PROXIES` 要加对端内网 IP。

### 600 秒 TTL 下的切换设计

TTL 600s 意味着「改 DNS 后最多 10 分钟才全量生效」，所以切换要按「先止血、再切换」设计：

1. **B 挂**：入口在 A，`upstream` 健康检查自动摘除 B → 用户无感，**不需要动 DNS**。
2. **A 挂**：DNS 改到 B 的 IP（TTL 600 → 最坏 10 分钟）。这 10 分钟里已缓存的客户端仍打 A → 表现为「一部分人能进、一部分人进不去」。缓解：B 上线一个**降级页**（nginx 直接返回维护页 + App 侧提示），比让用户看到超时好。
3. 因为接受 15 分钟接管，600 秒 TTL 是够用的——**但前提是切换动作被写成 3 条命令**，别临场想。

## 5. AWS 这台机器的正确用法

| 用途 | 做法 | 收益 | 注意 |
|---|---|---|---|
| **海外边缘缓存** | nginx 反代 `https://chat.shiliu153.cn`，缓存 `/media/`（图片/缩略图）与静态资源 | 海外用户图片加载快；省阿里云带宽 | ⚠️ **`/api/v1/` 绝不能缓存**：宝塔默认 `proxy_cache_key` 不含 `Authorization` 且忽略 `Vary`，会跨用户串数据（`README.md:459` 已记录这个坑） |
| **异地备份** | 阿里云每日 `mysqldump` + 媒体 `rsync` 推到 AWS | A 机房整体故障时还有一份 | 备份含个人信息 → 同样涉及出境合规，**建议加密 + 只留加密包** |
| **外部探针** | 从 AWS 每 5 分钟探 `/healthz`、`/readyz`、WS 握手 | 比本机探针更真实（能发现公网/证书/备案问题） | 探针失败要能告警到你手机 |
| **降级页** | A 挂时把域名临时指到 AWS，返回维护页 | 比「连接超时」体验好 | 需要证书覆盖该域名 |

**AWS 不要做的事**：跑 Django、跑 imserver、挂 MySQL 从库、做 NFS、做入口反代全站流量。前四项见 §2；最后一项会把所有请求多绕 40ms 且增加一个跨境故障点。

### 边缘缓存的硬要求

```nginx
# AWS 上：只缓存静态与图片，API 一律不缓存
proxy_cache_path /var/cache/nginx/media levels=1:2 keys_zone=media:100m max_size=10g inactive=7d;

location /media/ {
    proxy_cache media;
    proxy_cache_valid 200 7d;
    proxy_cache_key "$scheme$request_method$host$request_uri";  # 含签名 query，天然按 URL 隔离
    proxy_pass https://chat.shiliu153.cn;
}
location / { proxy_pass https://chat.shiliu153.cn; proxy_no_cache 1; proxy_cache_bypass 1; }
```

- 图片 URL 带签名（`?e=...&s=...`），缓存键含 query → 过期后自然回源，不会把失效链接缓存成永久可用。
- `proxy_cache_lock on;` 防回源击穿。
- 证书：AWS 侧用 Let's Encrypt 独立签一份（不要跟阿里云共享私钥传输）。

## 6. RTO 矩阵（600 秒 TTL 版）

| 故障 | 影响 | 恢复方式 | 实际 RTO |
|---|---|---|---|
| B 挂（R1 形态） | 无感 | upstream 自动摘除 | 0 |
| A 挂（R1） | 全站不可用 | 提升 B 的从库/副本 → 改 `.env` → 重启 → 改 DNS | **10–15 分钟**（DNS 占大头） |
| A 挂（R2 单机） | 全站不可用 | 修机器 / 从备份恢复 | 30 分钟–数小时 |
| 单机 CPU 打满（今天） | 全站变慢/超时 | 无横向手段，只能等或重启 | 不可控 |
| AWS 边缘挂 | 海外访问变慢（回源直连） | 摘掉 DNS 记录或修 nginx | 0（不影响主站） |

## 8. 需要你拍板的 2 件事

1. **AWS 在哪个 region？**（香港 / 新加坡 / 东京 / 美国 / AWS 中国区）
   - 决定 §2.4 合规红线是否成立；
   - 决定边缘缓存对目标用户是否真有用（如果用户全在国内，AWS 边缘基本没收益）。
2. **你要的是「容量」还是「不挂站」？**
   - 容量 → 先 R2 升配（当天生效、零风险），不够再 R1；
   - 不挂站 → 必须 R1（同云第二台），因为跨云做不到。
   - 两个都要 → R1 + R2，分两步走。

## 9. 提高容量的四条路（以及悉尼的位置）

「提容量」不等于「加机器」。四条路里只有第 ③ 条受地域约束。

| # | 手段 | 成本 | 预期收益 | 受地域限制 |
|---|---|---|---|---|
| ① | 单机优化：候选池/广场的 N+1（`select_related`/`prefetch_related`）、Redis 缓存首页与候选池、gunicorn `gthread` 调参、MySQL 索引复核 | 0 元 / 1–2 天 | 2–3×（当前 CPU 热点在刷卡与广场） | ❌ |
| ② | 升配 2C2G → 4C8G | +¥100–200/月 | 2–3×（瓶颈是核数） | ❌ |
| ③ | 同域加一台（本文件 §4） | +¥60–100/月 | ~2×，且 B 挂无感 | ✅ 必须与 MySQL/Redis 同 VPC |
| ④ | 媒体/静态外置（对象存储 + CDN） | 按量 | 省带宽与 TLS/IO 的 CPU | ❌（但涉数据出境） |

**顺序：① → ② → ③ → ④。**

### 为什么 ③ 必须同域

跨云共享数据层的前提不成立，量化如下（假设一个列表请求 8 条串行 SQL）：

| 数据层位置 | 单条 SQL 往返 | 一个请求的 DB 时间 | 可用性 |
|---|---|---|---|
| 同机（今天） | ~0.1ms | ~1ms | 基线 |
| 同地域不同可用区 | ~0.3–1ms | ~8ms | ✅ 可用 |
| 阿里云 ↔ AWS 悉尼（RTT 150–200ms，估算，需 `mtr` 实测） | 150–200ms | **1.2–1.6s** | ❌ 不可用 |

「同域」不要求同可用区、同机架：VPC 内网 1ms 以内即可。

### 悉尼（ap-southeast-2）的定位

| 能做 | 不能做 |
|---|---|
| 海外静态/图片边缘缓存（仅对澳/东南亚用户有意义） | 跑 Django（§2.1） |
| 异地加密备份、境外外部探针 | 挂 MySQL 从库 / Redis 副本（跨境复制不稳且涉出境） |
| 降级维护页 | 做全站入口反代（给国内用户 +150ms，且多一个跨境故障点） |
| 图片处理 offload（只读，不回写主库） | IM 双活节点（§2.3） |

> 若目标用户主要在澳洲/东南亚，正确做法不是「阿里云 + 悉尼双活」，而是**整套迁到 AWS 悉尼、两台同 region**；跨云混合是最差形态。

## 10. 这份方案明确不做的事

- ❌ 不设计「AWS + 阿里云 双活共享数据库」——物理上做不到，硬做出来是每天几百毫秒的响应。
- ❌ 不用 DNS 轮询做负载均衡——600 秒 TTL + 无健康检查 = 故障时一半用户打不通。
- ❌ 不引入 K8s / 服务网格 / 跨云专线——2C2G 规模，故障面远大于收益。
- ❌ 不在境外存储明文个人信息（备份也要加密）。
