# 单机容量基线：AWS t3.small（悉尼入口机）

> 测量日期：2026-11-13 16:42–16:44（Asia/Shanghai）
> 机器：`13.211.212.232`（`i-0eba990451c2d2e2d`，t3.small / 2 vCPU / 1905 MB）
> 拓扑：P1 单机栈（nginx + Django-A + imserver-A + MySQL + Redis + Celery），见 `README.md`
> 工具：`perf/run.py`（仓库自带），场景 `api_read` = `GET /api/v1/app/config`

## 1. 为什么现在还测这个

最终要回答的是「两台比一台快多少」。两台还没起来（安全组未放行），但**单机基线必须先有**，
否则到时候只有一个孤立的「双机 xx rps」，没有分母。

本表就是那个分母，且**口径统一**：同一台机器、同一个 `perf/run.py`、同一条访问路径
（经 nginx `127.0.0.1:8080`，也就是真实用户路径，不是直连 gunicorn）。

## 2. 结果

| 场景 | 并发 | 总量 | **rps** | p50 | p90 | p95 | p99 | 错误 |
|---|---|---|---|---|---|---|---|---|
| `api_read`（`/api/v1/app/config`） | 100 | 24 140 | **801.3** | 122 ms | 130 ms | 145 ms | 170 ms | 0 |
| `api_read` | 400 | 23 437 | **767.9** | 511 ms | 553 ms | — | 609 ms | 0 |
| `api_write`（`POST /discovery/swipe`，50 账号） | 50 | 2 298 | **74.9** | 659 ms | — | 708 ms | 796 ms | 0.13%（3×404） |
| `api_health`（`/api/v1/health`） | 100 | 9 629 | — | — | — | — | — | **79%（429 限流）** |

读法：

- **读：100 → 400 并发，rps 从 801 掉到 768（−4%），但 p50 从 122ms 涨到 511ms（×4.2）。**
  典型的「已经到顶、只是排队变长」：单机读吞吐天花板约 **800 rps**（此路径）。
- **写：约 75 rps，p50 659 ms** —— 比读慢一个数量级，与仓库既有结论一致（写路径受 DB 事务与 IM 副作用拖累）。
- 全程几乎 0 个 5xx：是被排队/限流，不是被打崩。

## 3. 三个必须写清楚的坑

### 3.1 `api_health` 不能用作压测目标

`/api/v1/health` 有 IP 级限流；压测器从 `127.0.0.1` 单 IP 打过去，7627/9629 直接是 `429`。
**测出来的是限流阈值，不是容量。** 要测框架开销请改用 `api_read`，或在测试环境临时放宽该接口的限流。

### 3.2 t3.small 的 CPU 积分会污染长时间压测

t3.small 基线算力只有 **20% × 2 vCPU = 0.4 vCPU 持续**（24 积分/小时）。
本次两轮各 30 秒，消耗约 1–2 积分，结果可信；
但**任何持续数分钟以上的压测都会耗尽积分并限速到 0.4 vCPU**，那时测到的是积分余额，不是架构容量。

> 结论：做「双机 vs 单机」对比时，两轮必须**同等时长、同等并发、背靠背**跑，
> 或者先把两台升到 `t3.medium`（基线 40%）。设计稿 §7.1 已把这条列为 P4 的前置。

### 3.3 压测器和被测服务同机

按 `perf/README.md` 的铁律，HTTP 容量测试在服务器本机跑（打 loopback），避免测到公网出口带宽。
代价是压测器与 gunicorn 抢同样 2 个核，所以**这个数字是保守下界**，
但也正因为两边口径一致，单机/双机之间仍然可比。

同机测量会看到 `load1 ≈ 1.6–2.6`、`mem_used ≈ 1.25 GB / 1.9 GB`。

### 5.1 写路径实测的两个坑（已踩）

1. **目标 id 必须真的存在，且 `{i}` 是全局自增。** 首次跑 `--i-start 200` 时，
   800 次请求后就越过 1002 个账号的上界，结果 **3211/4014 是 404**，
   而 404 比 200 快得多 —— 于是「rps 132.5」是假象（被快失败的请求灌高的）。
   改成 `seed_scale_users --count 5000` + `--i-start 2000` 才拿到干净的 74.9 rps。
   **看到 `codes` 里 404 占比高时，不要相信那个 rps。**
2. **`perf_tokens` 有生产环境保护**：`DEBUG=0` 时默认拒绝签发，需显式加 `--allow-production`。
   产物是**活的 access 令牌**，压测结束必须立刻删除（本次已 `rm /tmp/headers.jsonl`）。

## 6. 与阿里云生产口径的关系

仓库既有基线（[capacity-and-reliability.md](../../docs/ops/capacity-and-reliability.md)）
记录阿里云 2C2G 上 `GET /app/config` **476 rps @100 并发**，与本次 **801 rps** 不是同一口径：

| 差异 | 阿里云基线 | 本次 |
|---|---|---|
| 访问路径 | 直连 gunicorn `127.0.0.1:8000` | 经 nginx `127.0.0.1:8080` |
| 机器 | 阿里云轻量 2C2G（有观测栈在跑） | AWS t3.small（突发积分充足） |
| 用途 | 「生产在什么条件下多少」 | 「AWS 这套的双机对照分母」 |

**不要把两个数字直接相减或相除**。要比就跟自己同口径的历史数字比。
