# 内网直连切换（2026-11-13 晚）

> 前一阶段两台机器之间靠 **SSH 隧道**缝起来（`aws login` 会话过期、改不了安全组）。
> 凭证恢复后切成 **VPC 内网直连**，本文记录改了什么、以及直连后重测的数字。

## 1. 一个必须先更正的事实

**公网 80/443 一直是放行的。** 两台机器共用的 `sg-05777d46564139b71` 里早有
`80 / 443 / 22 / 41631 ← 0.0.0.0/0`。

之前「入口机 80 探测失败」的原因是**上面没有进程在监听** —— P1 部署时用的是
`--http-port 8080`，不是安全组拦的。设计稿 §2.2 与 §8 里「80/443 未放行」的说法**作废**。
（要让 Let's Encrypt 的 HTTP-01 走 80，需要重新渲染成 `--http-port 80`，那是部署动作，不是安全组动作。）

## 2. 真正缺的是内网业务端口

新增 5 条安全组规则，来源全部锁到**对端单个内网 IP**（不是整个 VPC 网段）：

| 目标 | 端口 | 来源 | 规则 ID |
|---|---|---|---|
| EDGE `sg-01f09c2e856ac986d` | 3306, 6379 | `172.31.35.181/32`（APP） | `sgr-0aa1a6309fdaa36fb` / `sgr-0d11eaf17becf9a43` |
| APP `sg-0de7b55570137e50f` | 8000, 9100, 9101 | `172.31.14.4/32`（EDGE） | `sgr-02fdf711c5aacd5b6` / `sgr-03b6833503b74cf39` / `sgr-0b6cc85760e709505` |

## 3. 一个 Docker 陷阱：`internal` 网络不能发布端口

MySQL/Redis 原先只在 `backend`（`internal: true`）网络里，没有发布到宿主机 ——
所以**光开安全组不够**，应用机根本连不到。

而给它们加 `ports:` 一开始**不生效**：`HostConfig.PortBindings` 有值，但
`NetworkSettings.Ports` 是 `null`、宿主机没有监听。隔离实验确认了原因：

```
普通 bridge 网：-p 172.31.14.4:18099:80  →  172.31.14.4:18099->80/tcp   ✅
internal 网   ：-p 172.31.14.4:18098:80  →  80/tcp（无映射）             ❌
```

**Docker 不允许给「只挂在 internal 网络上的容器」发布端口。**
修法见 `compose.edge.data-ports.yml`：给 mysql/redis 额外接一张**专用的非 internal 网络**
`chatapp_dataedge`（只有这两个容器接入，nginx 依然没有到 3306/6379 的路由，保住 M-6 的隔离意图）。

## 4. 改动清单

| 位置 | 改动 |
|---|---|
| 安全组 | 5 条内网规则（见 §2） |
| EDGE `compose.edge.data-ports.yml`（新增） | mysql/redis 绑 `172.31.14.4`，加 `chatapp_dataedge` 网络 |
| EDGE ufw | 放行 `172.31.35.181 → 3306/6379` |
| EDGE `nginx/edge.conf` | 上游从 `172.28.0.1:18000/19100/19101` 改成 `172.31.35.181:8000/9100/9101` |
| APP `compose.app.yml` | web 绑 `172.31.35.181:8000`；imserver 绑 `172.31.35.181:9100/9101` |
| APP `secrets/*.env` | `DB_HOST=172.31.14.4`、Redis/Broker 指向 `172.31.14.4:6379`、`IM_SELF_URL=http://imserver:9101` |
| APP ufw | 放行 `172.31.14.4 → 8000/9100/9101`；**删掉**全部隧道规则 |
| 两条 SSH 隧道 | **已拆除**（`fuser -k` 清端口） |

> `bin/topology.sh` 是隧道时代的工具，现在**只保留 `verify` 有意义**；
> `apply` / `teardown` 已不适用。下一轮会把它改写成「直连模式自检」。

## 5. 直连后重测（同口径，各 30 秒）

### HTTP

| 指标 | 单机 | 隧道双机 | **直连双机** | 相对单机 |
|---|---|---|---|---|
| 读 @100 并发 | 801 rps / p50 122ms | 1 215 / 82.5ms | **1 456 / 52.4ms** | **+82%** |
| 读 @400 并发 | 768 rps / p50 511ms | 1 229 / 330ms | **1 434 / 208ms** | **+87%** |
| 写 @50 并发 | 74.9 rps / p99 796ms | 96.2 / **p99 1 060ms** | **111.9 / p99 624.5ms** | **+49%** |

**直连把隧道时代的两个疑点都解决了：**

1. 读吞吐 1 215 → **1 456 rps**（+20%），p50 82.5 → **52.4ms**；
2. **写路径 p99 的退化消失了**：796（单机）→ 1 060（隧道）→ **624.5ms（直连）**。
   之前的判断「p99 变差是隧道代价」得到证实。

### IM

| 跑法 | p50 | p99 |
|---|---|---|
| 单节点（200 连接） | 1 752 ms | 1 872 ms |
| 隧道双机 | 1 265 / 1 494 ms | 1 463 / 1 707 ms |
| **直连双机** | 1 174 / 1 333 ms | 1 816 / 1 920 ms |

**IM 依旧没有实质提升（p50 略降、p99 略升，在噪声范围内）。** 这印证了原结论：
IM 的瓶颈是**共享的 MySQL/Redis 单点**（都在 EDGE 那 2 个核上），换掉隧道不改变这一点。
要提 IM 吞吐，顺序仍是「先把数据层从入口机拆出去 → 再谈加 imserver 节点」。

## 6. 压测数据踩的坑（补充）

`accounts_user` 的 id 空间是**稀疏**的（实测分布：`0-999` 有 999 个、`1000-1999` **只有 3 个**、
`2000-5999` 基本满、`6000+` 只有 6 个）。写压测的 `{i}` 是全局自增，
**起点落进空洞段就会压出一片 404**，而 404 比 200 快得多，会把 rps 虚高：

| `--i-start` | 404 占比 | 得到的 rps | 可信? |
|---|---|---|---|
| 500 | 1000/3688（27%） | 120.9 | ❌ 撞进 `1000-1999` 空洞 |
| 3000 | 614/3617（17%） | 119.8 | ❌ 撞到 `6000+` 尾部 |
| **2000** | **3/3412（0.09%）** | **111.9** | ✅ 密集段 |

**判据：先看 `codes` 里 404 占比，超过 1% 就不要相信那个 rps。**
